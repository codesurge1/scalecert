## Database schema

`db/schema.sql` is the single source of truth for a **fresh** apply of the database (ADR-0002, ADR-0005) — never dashboard clicks. For a purely additive change to an already-provisioned (live) project, a standalone idempotent script may accompany the same `schema.sql` edit under `db/migrations/` (ADR-0007, a narrow exception — not a general migration-file workflow): `002_registration_fields.sql` (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, the 21 `instruments` columns below), `003_pdf_certificate_and_verify.sql` (the `discrepancy_reports` table plus two `SECURITY DEFINER` functions, ADR-0009), `004_disturbance_test_types.sql` (`feat/disturbance-test-forms` — five `ALTER TYPE test_type ADD VALUE IF NOT EXISTS` statements, nothing else; **must be run against a live project before deploying this task's backend code**, or its first insert of one of the new test types fails with a Postgres enum error), `005_test_runs.sql` (`feat/test-runs-conditions` — the `test_runs` table plus nullable `run_id` columns on `test_readings`/`test_results`, ADR-0010; purely additive, no backfill required — see below), and `006_damp_heat_endurance_test_types.sql` (`feat/damp-heat-endurance` — two more `ALTER TYPE test_type ADD VALUE IF NOT EXISTS` statements, same "run separately, not in one transaction" caveat as 004). The human operator still runs each by hand against the live project; nothing here applies it automatically.

Nine tables:
- **profiles** — one row per `auth.users` row, holds `role` (technician/approver/admin) and `full_name`. Created by `handle_new_user()` on signup.
- **instruments** — the registered NAWI: accuracy class, `e_value`/`d_value`, Max/Min capacity, indication type, the `is_mobile`/`is_multi_interval` flags that gate the conditional tests, and (ADR-0007) 21 nullable columns capturing the rest of OIML R 76-2 page 6's "General information concerning the type" report form: identity (`applicant`, `instrument_category`), power supply (`u_nom`/`u_min`/`u_max`/`mains_frequency`/`battery_u_nom`), `printer_status`, `zero_device_type`, `tare_device_type`, `initial_zero_setting_range_pct`, `temperature_range_min`/`temperature_range_max`, load cell (`load_cell_manufacturer`/`load_cell_type`/`load_cell_capacity`/`load_cell_number`/`load_cell_class_symbol`), `software_version`, `identification_no`, `interfaces`. All nullable — a technician can register with just the core (identity + e/Max/Min) and leave the rest for later. `printer_status`/`zero_device_type`/`tare_device_type` are plain `text` columns (not DB enums); their closed option sets are enforced as `Literal[...]` types at the Pydantic contract layer (`backend/app/contracts/instrument.py`), the same "validated above the DB" philosophy `session_test_selection.zero_device_status` already used, but for these three actually enforced, not just commented.
- **test_sessions** — one verification session per instrument visit: status, certificate number, approval trail, and the report-header patch fields (see below).
- **session_test_selection** — which of the six `test_type`s apply to this session, with an NA reason where they don't and a per-test `zero_device_status`.
- **test_runs** (`feat/test-runs-conditions`) — a labelled run of a test under a given set of conditions (`run_label`, `conditions` JSONB, `ordinal`). Exists because several OIML tests are the SAME procedure re-run more than once, where the test IS the comparison between runs: clause 1 Weighing at multiple temperatures (page 9's "Initial" + several °C rows), clause 13 Damp heat (initial → high-temp/85%RH → final), clause 15 Endurance (initial → after N cycles → final). One table across every `test_type` (same hybrid design as `test_readings`/`test_results`, immediately below) — as of `feat/damp-heat-endurance`, THREE routers are now wired to it (Weighing, Damp heat, Endurance), proving out the "generic, reused unmodified" design `feat/test-runs-conditions` set out to build. `unique (session_id, test_type, ordinal)` — the ordinal is always server-derived (next available slot), never client-supplied, same "server derives it" discipline as the Weighing load sequence's `L`. Endurance's own "b) Performance of the test" cycling step (number of loadings, load applied) is recorded in the Final run's own `conditions` (ADR-0011) — no new column.
- **test_readings** — raw technician input per test, one row per reading (or per series/position where applicable), keyed by `test_type`. No schema change was needed to add Zero/tare, Repeatability, Eccentricity, Discrimination, Sensitivity, or Tilting (all six added across this task and the previous one): every `test_type` enum value (`discrimination`, `tilting`, `sensitivity` included) and every discriminator column (`direction`, `series_no`, `position_no`) was already present, unused, from the original schema (ADR-0005) — added ahead of when they'd be needed. Each test uses exactly the discriminator(s) it needs and leaves the rest null: a regular Weighing-sequence reading always sets `direction`; a zero/tare reading (`test_type='weighing'` too — see the enum comment below) always leaves `direction` null, which is what distinguishes the two; `repeatability` rows set `series_no` (1 or 2); `eccentricity` rows set `position_no` (1-4); `discrimination`/`sensitivity` rows use only `sequence_no` (the check-load index); `tilting` rows set BOTH `sequence_no` (repurposed to encode the phase — 0/1/2 for unloaded/mid-load/Max, since the column is `not null` and Tilting has no real "sequence" of its own) and `position_no` (1-5). `run_id` (`feat/test-runs-conditions`) is a nullable FK to `test_runs` — see "Runs, conditions, and cross-run comparison," below.
- **test_results** — computed verdicts derived from readings, keyed by `test_type` and optionally `reading_id`. Also gained a nullable `run_id` FK, mirroring `test_readings` (same task).
- **audit_log** — append-only record of actions taken against a session.
- **discrepancy_reports** (this task) — public, login-free "report a problem with this certificate" submissions (`id`, `certificate_number`, `description`, `contact`, `created_at`), no FK to `test_sessions` (see the Public verification section, below, for why). The only table anyone with no account may INSERT into; only `admin` may ever read them back.

Enums: `user_role`, `accuracy_class`, `verification_type`, `session_status`, `indication_type`, `test_type` (twelve values as of `feat/damp-heat-endurance`: the original six, plus `voltage_variations`/`ac_mains_dips`/`electrical_bursts`/`electrostatic_discharges` — see Record-only disturbance tests, below — plus `damp_heat`/`endurance`).

**Hybrid design.** `test_readings` and `test_results` are each a single table across all six `test_type`s, not one table per test. Test-type-specific fields live in a `data` / `result` JSONB column; the shape of that JSON is enforced by a Pydantic model per `test_type` at the API layer, not by the database. This keeps the schema stable as test-specific fields evolve, at the cost of the DB not being able to validate that shape itself.

**Report-header patches.** Four fields were added to `test_sessions` from the RRSL visit (Part D.3): `observer_name`, `test_date`, `environmental_conditions` (start/max/end × Temp/Rel.h/Time/Bar.pres, JSONB), and `remarks`. A fifth patch, `zero_device_status`, lives on `session_test_selection` instead, since it's per-test rather than per-session.

**Resolution during test.** The report form's "resolution during test" field is not its own column — it renders as `COALESCE(d_value, e_value)` from `instruments`.

**Certificate numbering.** `certificate_number` on `test_sessions` is assigned only at issue time (`POST /api/sessions/{id}/issue` — Session lifecycle, below), formatted `SC-{YEAR}-{6-digit sequential}` drawn from `certificate_number_seq` — never before issue, and issue is itself only reachable from `approved` (see CLAUDE.md guardrails). Consumed atomically via the `public.issue_certificate_number()` Postgres function (ADR-0008), the one narrow schema addition this task made — PostgREST has no way to call `nextval()` on a bare sequence from the JWT-scoped client otherwise.

**Runs, conditions, and cross-run comparison (`feat/test-runs-conditions`, ADR-0010; now consumed by Damp heat/Endurance, `feat/damp-heat-endurance`, ADR-0011).** The structural insight: several OIML type-evaluation tests are the SAME procedure re-run under different conditions, where the test IS the comparison between runs — clause 1 Weighing at multiple temperatures (page 9's "Initial" + several °C rows), clause 13 Damp heat (a/b/c: initial at reference temp → high temp + 85% RH → final back at reference temp), clause 15 Endurance (a/c: initial test → cycle N times → final test, durability error = `|Ec_initial − Ec_final|` vs mpe). All three reuse the existing Weighing engine/form. `feat/test-runs-conditions` built the runs/comparison infrastructure without wiring Damp heat or Endurance themselves; `feat/damp-heat-endurance` is that infrastructure's first real payoff — both tests are built with almost no new plumbing, exactly as the earlier task's generic design intended.

- **`test_readings.run_id`/`test_results.run_id` are nullable, and NULL means "the default/only run."** This is the entire backwards-compatibility mechanism, deliberately: every reading/result row written before `feat/test-runs-conditions`, and every reading of a test that never grows beyond one run (Zero-tare, Repeatability, Eccentricity, Discrimination, Tilting, Sensitivity, Voltage variations, the three record-only disturbance tests), simply has `run_id = null` and behaves completely unchanged. Damp heat and Endurance are different: EVERY reading of theirs has a real `run_id` — there is no implicit default run for either, since the run structure (a/b/c, a/c) IS the test, not an opt-in extra (unlike Weighing's own optional multi-temperature runs). Their contracts' `run_id` field stays `Optional[str]` anyway, for shape consistency with Weighing's, even though in practice it's always supplied.
- **Three routers are now wired to this, not one.** Weighing (`feat/test-runs-conditions`): `GET/POST /api/sessions/{id}/weighing/runs`, `GET .../weighing/readings`/`POST .../weighing/readings` (both gained an optional `run_id`), `GET .../weighing/runs/compare`. Damp heat and Endurance (`feat/damp-heat-endurance`) mirror this shape exactly under `/damp-heat`/`/endurance`, PLUS a `POST .../setup` endpoint each (idempotent — creates whichever of that test's FIXED run labels don't already exist, a concept Weighing's own optional, technician-labelled runs never needed) — see API surface, below, for the full list. `app/contracts/runs.py`/`app/repositories/runs.py`/`app/services/runs.py` needed exactly one addition to serve all three — `runs_service.ensure_fixed_run_labels` (which of a test's known-in-advance labels don't exist yet) — everything else (`next_ordinal`, `compare_records`, the repository CRUD) is used completely unmodified by Damp heat/Endurance.
- **Cross-run comparison is a pure, tested ENGINE function** (`engine/comparison.py`, `compute_run_comparison`) — `variation_error = |Ec_a − Ec_b|`, PASS iff `variation_error <= mpe` (limit inclusive, same convention as `compute_weighing_result`). Order of the two runs never matters (it's a magnitude); every input is a required, explicitly-typed `Decimal`. `app/services/runs.py`'s `compare_records` matches two runs' reading records by `(sequence_no, direction)` — the same load tested in each run — and calls this function once per matched load; loads present in only one run are silently skipped (nothing to compare yet), never an error. Generic over any reading-record shape carrying `sequence_no`/`direction`/`Ec`/`mpe` (a `Protocol`, not a Weighing-specific type) — `DampHeatReadingRecordOut` and `EnduranceReadingRecordOut` both satisfy it with zero changes to `compare_records` itself.
- **Endurance's own aggregate — `compute_durability_check`, new this task.** The form's own extra verdict (page 47) isn't "does one load's variation pass" but "does EVERY load's durability error stay within mpe" — a genuinely different aggregation, the same "whole-set property" shape as `compute_repeatability_series`'s spread check or `compute_tilting_loaded_check`'s max-deviation check. `engine/comparison.py`'s `compute_durability_check(comparisons)` wraps a list of `RunComparisonResult`s into a `DurabilityCheckResult(comparisons, all_passed)` — `all_passed` is `False` on an empty list (nothing submitted yet is never a pass) and requires every entry's own `passed` to be `True`. `app/services/runs.py`'s `durability_check_from_entries` bridges `compare_records`' `RunComparisonEntryOut` output back into the bare `RunComparisonResult`s this function needs (same fields, plus load identity) rather than threading a second parallel return value through `compare_records` itself.

## Engine design

The `engine/` package (repo root, sibling to `backend/` and `frontend/`) is pure: standard library only, no FastAPI, Supabase, network, DB, or wall-clock imports — enforced mechanically by `tests/test_purity.py`, which walks every `engine/*.py` file's AST and fails if any top-level import resolves outside `sys.stdlib_module_names`.

All arithmetic uses `Decimal`, never `float` — a boundary verdict (e.g. `Ec == mpe` exactly) must not turn on binary floating-point rounding. Every function requires all of its inputs explicitly (no default values); a missing or wrong-typed input raises `TypeError`/`ValueError` rather than being guessed (`tests/test_input_validation.py` proves this for both the MPE lookup and the Weighing calculation).

**Accuracy-class derivation** (`engine/classification.py`, `classify_instrument`) — accuracy class is NEVER a free choice, for a registrant or for a client of any kind: it is derived, purely, from an instrument's own `e`/`Max`/`Min` (and `d`, if given) via OIML R76-1 Table 3, the same "server derives it, nothing downstream trusts a client-invented value" shape as the Weighing load sequence's `L`. This closes a real bug: the previous free-choice model let an instrument get registered as "Class III" with `n = Max/e = 15000` — which exceeds Class III's own `n_max` of 10000 — and that invalid combination later crashed the Weighing load-sequence endpoint, since `engine.load_sequence`/`engine.mpe.lookup_mpe` both trust the stored class's Table 6 band range and never re-derive or re-validate it themselves (that isn't their job — it's this module's, and it now runs at registration time, before anything is stored).
- **Table 3 data, reused from Table 6 rather than duplicated.** Each class's `n_max` is *exactly* the upper bound of that class's last `engine.mpe.BAND_TABLE` (Table 6) band — Table 6 only needs to define MPE bands up to where the class itself stops applying — so `classification.py` reads `n_max` directly off `BAND_TABLE` (`_n_max_for_class`) instead of keeping a second hardcoded copy that could silently drift out of sync. `n_min` and the Min-capacity-as-a-multiple-of-`e` requirement have no Table 6 equivalent and are Table 3's own data, entered once.
- **Six rows, not four.** Classes II and III each split into two rows by `e`'s own magnitude (a lower-`e` row and a higher-`e` row, each with a different `n_min`/Min requirement) — Table 3's actual shape, not a simplification. A given `e` can fall inside more than one class's applicable row at once; it's `n` and Min that discriminate. `classify_instrument` evaluates every row whose `e`-range the instrument's `e` falls into and returns every row that *also* passes on `n` and Min — zero, one, or more classes, most-precise-first (I, then II, then III, then IIII) — as a `ClassificationResult` (`engine/types.py`): `n` (always populated, even on failure, since it's useful in a rejection message), `qualified_classes`, and `reason` (populated only when `qualified_classes` is empty, naming exactly which class(es) were in range and which specific constraint — `n` too high/low, or Min too low — failed for each).
- **`e` must be 1, 2, or 5 × 10^k grams** (clause 3.4.2's standard verification-scale-interval sequence) — checked via `Decimal.normalize().as_tuple()`'s own digit tuple, never float/log-based math, so there's no rounding risk at the boundary. `d`, if given, is checked separately against clause 3.4.2's `d < e ≤ 10d` relationship. Either failing is a rejection with a specific reason, same as a Table 3 mismatch.
- **`min_capacity` is required here** — unlike `engine.load_sequence`'s `min_capacity`, which is optional for an unrelated reason (whether Min is tested as a verification anchor, not whether it's known). Every Table 3 row carries its own Min requirement, so classification cannot run at all without it.
- **Single-interval only, for now** — same limitation as `engine/load_sequence.py`; multi-interval classification (per-sub-range `e`/`n`/Min) is a known future extension, not handled here.
- Argument type/domain errors (not a `Decimal`; `e`/`max_capacity` `<= 0`; `min_capacity` `< 0`) raise `TypeError`/`ValueError` immediately — caller bugs, not legitimate "doesn't fit any class" business outcomes, which is what the returned `ClassificationResult.reason` is for.
- Validated by `tests/test_classification.py`: one clean valid case per class, `n`-at-exact-boundary cases (both ends), the bug scenario itself (`e=1g`, `n=15000` — proven to never again qualify for Class III, resolving instead to Class II when Min is adequate, and cleanly rejected with a reason when it isn't), Min-too-low cases, a genuinely multi-class-qualifying case, `e`-format validation (valid and invalid), and the `d`/`e` relationship.

**MPE lookup** (`engine/mpe.py`, `lookup_mpe`) — inputs: `accuracy_class`, `m` (load in multiples of `e`), `e` (for the grams conversion), `verification_type`. Looks up R76-1 Table 6 by class and `m`-band (upper bound inclusive, next band's lower bound exclusive of it); `initial`/`subsequent` return the table value as-is, `in_service` doubles it. Returns an `MpeResult` carrying not just the number but the band boundaries used (`band_lower_m`, `band_upper_m`) and the class/type/e/m it was computed from — so a result is traceable back to which row of Table 6 produced it, not just the resulting figure.

**Weighing calculation** (`engine/weighing.py`, `compute_weighing_result`) — `E = I + 1/2*e - deltaL - L`, `Ec = E - E0`, verdict `PASS` iff `|Ec| <= mpe` (limit inclusive). Returns a `WeighingResult` with the full derivation (`L, I, delta_l, E0, E, Ec, mpe, margin, passed`) plus the `MpeResult` that produced `mpe` — never just a boolean. `margin = mpe - |Ec|` so a near-miss is visible, not just a verdict.

**Validation.** The canonical worked example (Class III, e=1g, initial, load 300g → Band 1 → mpe=±0.5g; reading 300.4g → PASS; 300.6g → FAIL — `docs/plan.md` Phase 1) was written as a failing test *before* the engine existed, then implemented until green. Per CLAUDE.md, one example is a smoke test, not validation: no verdict is trusted until `tests/test_mpe_boundaries.py`'s boundary-value table passes — every Table 6 band edge from both sides for all four classes, the at-limit-inclusive/just-over verdict boundary in both directions, `in_service` doubling actually flipping a verdict, and the Max/Min ends of each class's table range.

**Load-sequence generator** (`engine/load_sequence.py`, `generate_load_sequence`) — produces the applied-load (`L`) sequence for a Weighing test, so the technician enters only Indication (I) and additional load (ΔL); `L` is never technician-entered. Inputs: `accuracy_class`, `e`, `max_capacity`, `min_capacity` (the sole genuinely optional argument — `Optional[Decimal]`, not a default), `verification_type`.

- **Two different load-count numbers — do not conflate them.** The 8.3.3 verification checklist's OIML-sourced minimum is ≥5 distinct test loads; that figure is fixed by the standard and does not change. This project's own working target, `MIN_VERIFICATION_LOAD_COUNT`, is 10 — a lab convention chosen because spreading more load points across the range gives a more thorough verification and matches common RRSL practice, exceeding OIML's own ≥5 minimum. It is **not** an OIML requirement of 10, and it is a coincidence of numbering, not the same figure, that a *different* "≥10" also appears in some visit-report material — that one is for full type evaluation, a separate, out-of-scope test battery. Conflating either of those two with each other, or with this project's target, would misstate what's regulatory-sourced versus a chosen convention.
- **Sourced anchors** (always present when applicable): Max; Min, but only if given and ≥100 mg (0.1 g, per A.4.4.1 — otherwise omitted, never clamped or guessed); every Table 6 band-transition load that falls within `[Min-or-0, Max]`. The transition loads are read directly out of `engine.mpe.BAND_TABLE` — the same table `lookup_mpe` uses — never a second hardcoded copy of the band edges.
- **The sequence now starts at 10e — a mandatory anchor, but an RRSL lab convention, not OIML-sourced.** The load run's first (lowest) load is ten verification scale intervals (`10 * e` — e.g. e=10g → 100g), tagged `LoadKind.TEN_E` and distinct from every sourced anchor and from a `fill` point. Added whenever `10e <= Max`; skipped outright for a tiny-range instrument where even `10e` would exceed Max (no clamping). If `10e` happens to land exactly on an already-claimed anchor — most commonly Min, on an instrument where `Min == 10e` — the generator's existing anchor-dedupe (by exact `L`) keeps the earlier, OIML-sourced anchor rather than adding a second entry at the same load; the sourced anchor wins that tie, `TEN_E` is simply not added. Counts toward `MIN_VERIFICATION_LOAD_COUNT` like every other anchor, so it reduces the number of Band-1 fills needed by one rather than growing the sequence past the target — the demo instrument (e=10, Max=30000, Min=200) now has 5 anchors (100, 200, 5000, 20000, 30000) and 5 fills, still totaling 10.
- **Band-1 fill spacing is a documented placeholder, not a sourced value.** OIML does not prescribe how many extra loads, or where, to place inside Band 1 beyond the mandatory anchors, and RRSL has not yet confirmed a convention (`docs/plan.md` Open questions). When anchors fall short of the target of 10, the gap is filled with points spread across Band 1 and SNAPPED to a round step — a "nice" 1/2/5 x 10^k increment, the same digit pattern clause 3.4.2 itself uses for `e` — so a fill lands on a realistic load like 500, 1000, or 2000 g, never on an arbitrary fraction like `885.714285714285714285714286` that raw even division of the interval would produce (`_nice_step_at_or_below`, `_round_fill_points_within_band_1`). The step is derived once from the ideal even spacing (`span / (count+1)`) and snapped DOWN to the largest nice value that still fits, guaranteeing at least as many round candidates as the raw spacing would have produced; if more candidates exist than needed, `count` of them are chosen at evenly-spaced indices across the candidate list (Decimal-based rounding, never a float division) so fills stay spread across the band rather than clustering at its low end. Anchors are never touched by this — only fill points move. Deterministic and reproducible either way (never random, so a certification record reproduces identically), explicitly labeled (`FILL_SPACING_STRATEGY`) as a convention pending RRSL confirmation, changeable in one place. Every `LoadEntry.kind` is `max` / `min` / `band_transition` (OIML-sourced), `ten_e` (the RRSL start-load convention above — mandatory but not OIML-sourced), or `fill` (convention) — `LoadEntry.is_anchor` is `True` for all but `fill`, so a report or UI can never present a placeholder fill point as a mandated one, while still distinguishing the two conventions (`ten_e`, `fill`) from the three genuinely OIML-sourced kinds by `kind` itself.
- **Bidirectional testing is not dropped, just deferred.** The plan requires each load tested going up and coming back down; this generator returns only the distinct ascending `L` values — expanding each into an "up" and "down" reading is the reading layer's job (Phase 2), not this module's.
- **Single-interval only, for now.** The generator assumes a single-interval instrument (one `e` across the whole range). Multi-interval instruments (`instruments.is_multi_interval`) — where `e` itself changes across sub-ranges — are a known future extension, not handled here.

**Zero/tare device accuracy** (`engine/zero_tare.py`, `compute_zero_tare_result`) — the Weighing checklist item's own zero/tare-device variant (CLAUDE.md: "Weighing (incl. zero/tare device accuracy)"). Same change-point family as Weighing (`E = I + 1/2*e - deltaL - L`, `Ec = E - E0`, PASS iff `|Ec| <= mpe`) — modeled as a thin wrapper delegating straight to `compute_weighing_result`, not a reimplementation, since the math is identical and only the load-derivation differs. `generate_zero_tare_checks(max_capacity, min_capacity)` produces a small, deterministic 3-point check-load list (0, an anchor, and 2× that anchor — the anchor is `min_capacity` when known, else a documented fallback fraction of Max, same "convention pending RRSL confirmation" status as `load_sequence.py`'s `FILL_SPACING_STRATEGY`) instead of a Table-6-anchored full sequence — "a few readings on the zero/tare device," never technician-entered.

**Repeatability** (`engine/repeatability.py`, `compute_repeatability_series`) — R76-1 A.4.5/A.4.10, structurally different from Weighing, not a variant of it. Two independent series, each at ONE fixed load (`generate_repeatability_load`: series 1 ≈ 50% of Max, series 2 = Max itself — R76-1's own two representative loads), nominally 10 readings per series. **No E0 correction** — `E = I + 1/2*e - deltaL - L` is checked directly, deliberately (R76-2 page 16's own form has no E0/Ec columns, only a single "Error, E" column). Two independent pass criteria per series: (a) every individual reading's `|E| <= mpe`; (b) the spread `Emax - Emin` (SIGNED `E`, not `abs(E)` — a positive and a negative error of equal magnitude produce a real, non-zero spread) `<= mpe`. A series passes only if both hold; each series has its own `mpe` since the two loads can land in different Table 6 bands (proven by a dedicated test case in `tests/test_repeatability.py`, not assumed). `compute_repeatability_series` takes the WHOLE series' readings at once, not one at a time like Weighing's per-reading engine call — the spread criterion is inherently a property of the full set, so there is no meaningful single-reading call here.

**Eccentricity** (`engine/eccentricity.py`, `compute_eccentricity_position`) — R76-1 A.4.7, "3.1 weights" (R76-2 page 12). Same Weighing change-point math, applied independently at each of 4 receptor positions (1=top-left, 2=top-right, 3=bottom-right, 4=bottom-left, clockwise — the page-12 sketch). The one structural difference from Weighing: **E0 is re-measured before each position**, never a shared session-level baseline — each position is a fully independent `compute_weighing_result` call with its own `E0` (proven in `tests/test_eccentricity.py`: two positions with identical `I`/`L`/`delta_l` but different `E0` produce different `Ec`, ruling out any shared/global zero state). `generate_eccentricity_load(max_capacity)` derives the one fixed test load shared across all 4 positions (a documented convention, ≈1/3 of Max, pending RRSL confirmation — same status as the other two conventions above), never technician-entered.

**Discrimination** (`engine/discrimination.py`) — R76-1 A.4.8 (R76-2 page 14). THREE genuinely distinct sub-procedures, one formula each, selected by the instrument's `indication_type` (derived server-side — see Contracts/API surface below — never a client choice, same discipline as accuracy_class):
- `compute_discrimination_analog` (A.4.8.1, analog indication) — apply `L`, read `I1`; apply an extra load `= |mpe|`, read `I2`. Pass: `I2 - I1 >= 0.7 * mpe`.
- `compute_discrimination_non_self_indicating` (A.4.8.1, non-self-indicating) — apply `L`; apply an extra load `= 0.4 * |mpe|`; observe whether there's a visible displacement. Purely qualitative — `passed` IS the observed boolean, no threshold comparison at all.
- `compute_discrimination_digital` (A.4.8.2, digital) — apply `L`, read `I1`; remove the load, re-add it in 1/10 `d` increments up to 1.4`d`, read `I2`. Pass: `I2 - I1 >= d`. No `mpe`/`accuracy_class`/`verification_type` involved at all — a structurally different formula, not a variant of the other two. **Not required for verification of digital-indication instruments per clause 8.3.3** — implemented for spec completeness only; the frontend keeps the whole Discrimination test N/A for a digital instrument (`testChecklist.js`), so this sub-procedure is reachable only by direct API/engine use, never through normal navigation.

`generate_discrimination_checks(max_capacity, min_capacity)` produces the same style of 3-point check-load list as Zero-tare's own generator (low anchor / midpoint / Max) — a documented convention, not OIML-sourced, matching page 14's own 3-blank-row sub-tables.

**Sensitivity** (`engine/sensitivity.py`, `compute_sensitivity`) — R76-1 A.4.9 (R76-2 page 15), non-self-indicating instruments only (clause 6.1). Apply `L`; apply an extra load `= |mpe|`; measure the permanent displacement (mm) of the indicating element. The pass threshold (`sensitivity_threshold_mm`) is **tiered by accuracy class AND Max**, not a single number: 1 mm for class I/II (regardless of Max); 2 mm for class III/IIII with Max ≤ 30 kg; 5 mm for class III/IIII with Max > 30 kg. `max_capacity` is stored in grams throughout this app, so the boundary is `MAX_THRESHOLD_GRAMS = 30000`, compared directly — `tests/test_sensitivity.py` proves both sides of that exact boundary, not just the tier logic in the abstract. Reuses the same 3-point check-load generator convention as Discrimination.

**Tilting** (`engine/tilting.py`) — R76-1 A.5.1/A.5.1.1-A.5.1.3 (R76-2 page 20), mobile instruments only (clause 4.18). Implements the **minimal 8.3.3/4.18 slice that R76-2's own page-20 report form itself asks for** — reference position (1) plus 4 tilted positions (2-5), each read unloaded then at two loaded rows (a mid load and Max) — not the full, separately-repeated Annex A.5.1 battery beyond what that one report page captures.
- `Ev = Iv + 1/2*e - deltaLv - L`, `Ecv = Ev - Ev0` — identical to Weighing's formula, so every reading here is computed via `compute_weighing_result` (`compute_tilt_unloaded_reading`: `L=0, E0=0`, so `.E` IS that position's `Ev0`; `compute_tilt_loaded_reading`: takes that position's own `Ev0` as `E0`) — never reimplemented.
- The one genuine structural difference from Eccentricity: here `E0` is measured **once per position** (from that position's own unloaded reading) and **reused for both loaded rows** at that position — Eccentricity re-measures `E0` fresh before every single reading, Tilting does not.
- Two independent pass criteria, each its own aggregation function (mirroring Repeatability's series-is-a-whole-set-property shape): `compute_tilting_unloaded_check` — `|E1,0 - Ev,0|_max <= 2e` across whichever positions have been measured (position 1 must be among them); `compute_tilting_loaded_check` — checked independently at EACH loaded row — `|Ec1 - Ecv|_max <= mpe` for that row's own load (the mid load and Max can land in different Table 6 bands, so each gets its own `mpe`, same principle as Repeatability's two series — `tests/test_tilting.py` proves this with a real differing-band case).
- `generate_tilting_mid_load(max_capacity)` derives the mid load (≈50% of Max, a documented convention — the real form's own "L =" box is blank, filled by the lab, so there's no OIML-sourced figure to anchor to).
- **Not modeled:** the standard's own "(not valid for class II instruments, if not used for direct sales to the public)" carve-out on the unloaded criterion — `instruments` has no direct-sale flag; the criterion is always checked, and this gap is flagged in the form's own caption, not silently ignored.

**Cross-run comparison** (`engine/comparison.py`, `compute_run_comparison`) — the shared math behind "runs/conditions" (Database schema, above): `variation_error = |Ec_a − Ec_b|` for two runs' corrected error at the SAME load, PASS iff `variation_error <= mpe` (limit inclusive). Returns a `RunComparisonResult` (`Ec_a, Ec_b, variation_error, mpe, margin, passed`) — never just a boolean, same discipline as every other engine result in this app. Deliberately order-independent (a magnitude, not a directional delta) and deliberately generic: it takes two bare `Ec`/`mpe` Decimals, not a `WeighingResult`, so any test whose own change-point math produces an `Ec`/`mpe` pair can call it unmodified — proven true by `feat/damp-heat-endurance`, which does exactly that for both Damp heat (informational drift display) and Endurance (its own pass/fail gate, below). Boundary-value and sign-handling coverage in `tests/test_comparison.py`: variation error exactly at mpe from both sides, opposite-signed `Ec` values, both-negative `Ec` values, zero mpe requiring exact agreement, and that the two runs' order never changes the verdict.

**Endurance's durability check** (`engine/comparison.py`, `compute_durability_check`, added `feat/damp-heat-endurance`) — R76-1 A.6, R76-2 page 47's own extra column and verdict: the durability error due to wear and tear (`variation_error` between the Initial and Final runs) must be `<= mpe` for EVERY load, not just some. A genuinely different aggregation from a single `compute_run_comparison` call — the same "whole-set property, not a single reading" shape `compute_repeatability_series` (spread across a series) and `compute_tilting_loaded_check` (max deviation across positions) already established. Takes an iterable of `RunComparisonResult`s, returns a `DurabilityCheckResult(comparisons, all_passed)` — `comparisons` is the full list the verdict was derived from, never dropped for a bare boolean. `all_passed` is `False` on an empty list (nothing submitted yet is never trusted as a pass, mirroring `passed` defaulting `False` everywhere else in this app before any data exists) and type-checks every element is genuinely a `RunComparisonResult`. Tested in `tests/test_comparison.py`: all-passing, one-failing-load-fails-the-whole-check, a single passing entry, the boundary case (variation error exactly at mpe still passes), the empty-list case, non-`RunComparisonResult` elements rejected, and input order/tuple-ness preserved.

**Voltage variations and the record-only disturbance tests (`feat/disturbance-test-forms`) add NO new engine code.** Voltage variations (clause 11) calls `compute_weighing_result` directly at a fixed 10e load (`app/services/voltage_variations.py`) — the same formula, same function, zero new math, matching `zero_tare.py`'s precedent for reusing Weighing's engine at a different load. The four record-only disturbance tests (AC mains dips, electrical bursts, electrostatic discharges — built; surges, radiated EM, conducted RF, road-vehicle transients — deferred) have no engine at all: OIML's own pass rule for each is "check if a significant fault occurred," a physical-bench observation only a technician (with EMC equipment this software cannot drive or measure) can make — see API surface, "Record-only disturbance tests," below, for the full reasoning.

## Contracts / API validation layer

`backend/app/contracts/` holds the Pydantic v2 models that sit between the wire and the engine — one module per test, all seven now built. `weighing.py` was the first (the vertical slice); the other six follow its shape (`*ReadingSubmitIn`/`*ResultOut`/`*ReadingRecordOut` plus the engine-seam adapter functions), each with the differences its own test needs:
- `zero_tare.py` has no `direction` (unidirectional checks).
- `repeatability.py` has no `direction`/`E0`/`Ec` at all, and its primary output is `RepeatabilitySeriesOut` (a whole-series aggregate) rather than a per-reading result.
- `eccentricity.py` keeps `E0` as technician-submitted input (per-position, not session-level) and keys everything by `position_no` instead of `direction`.
- `discrimination.py` covers all THREE sub-procedures with one submit-in model (`DiscriminationReadingSubmitIn`, every variant-specific field `Optional`) and one output model (`DiscriminationResultOut`, `variant: Literal["analog","non_self_indicating","digital"]` says which one actually ran) — the service layer, not the contract, enforces which fields a given instrument's derived variant actually requires (`MissingFieldsForVariant` → 422). This is a deliberate deviation from "one narrow model per shape": three route paths for three sub-procedures of the same test would have scattered the "which variant applies" derivation across routes instead of keeping it in one place (`app/services/discrimination.py`).
- `sensitivity.py` follows the zero-tare shape closely (a 3-point check list, `SequenceNumberOutOfRange`), with `threshold_mm` carried on both the check and the result so a client always sees the tier that applied.
- `tilting.py`'s primary output, `TiltingStateOut`, is (like `RepeatabilitySeriesOut`) a whole-dataset aggregate, not a per-reading result — every pass-criterion field is `Optional`/`None` until enough readings exist to compute it (position 1, the reference, must be among what's submitted for that phase/row).
- `voltage_variations.py` (`feat/disturbance-test-forms`) follows the zero-tare shape (`*ReadingSubmitIn`/`*ResultOut`/`*ReadingRecordOut`, `L` server-derived) with `level_key: Literal["reference","lower","upper"]` in place of a `sequence_no`-indexed check list, and an extra optional `U` field (the power-supply voltage applied — informational, never fed into the engine call).
- `runs.py` (`feat/test-runs-conditions`) is generic across `test_type`, unlike every module above — `TestRunCreateIn`/`TestRunOut` mirror `test_runs` directly (Database schema, above), and `RunComparisonEntryOut`/`comparison_result_to_out` mirror `engine.types.RunComparisonResult` plus the load identity (`sequence_no`/`direction`) and the two run ids compared. `weighing.py` gained one additive field, `run_id: Optional[str] = None`, on both `WeighingReadingSubmitIn` (what the client may submit) and `WeighingReadingRecordOut` (what's read back) — omitted/null on either side means the implicit default/only run, so every pre-existing caller of these two contracts is unaffected.
- `damp_heat.py`/`endurance.py` (`feat/damp-heat-endurance`) each mirror `weighing.py`'s shape verbatim — `*ReadingIn`/`*ReadingSubmitIn`/`*ResultOut`/`*ReadingRecordOut` plus the same engine-seam adapter functions, calling the exact same `engine.weighing.compute_weighing_result` — this app's own established one-module-per-test convention (the same choice `zero_tare.py` already made for an identical reason) rather than reusing `Weighing*` classes directly for a different test's wire shape. `endurance.py` additionally has `EnduranceCyclingIn` (the non-computed b) step — `number_of_loadings: Optional[int]`, `load_applied: Optional[StrictDecimal]` — Decimal discipline still applies even though it's condition metadata, unlike Weighing's own free-form `conditions: Optional[dict]`, because this field IS validated input with a known shape, not opaque metadata) and `DurabilityCheckOut` (wraps `engine.types.DurabilityCheckResult`: `comparisons: list[RunComparisonEntryOut]` plus `all_passed` — never just the bare boolean).
- `disturbance.py` is structurally DIFFERENT from every model above — the first contract module in this app with no engine-seam adapter functions at all, because there's no engine to seam to (Engine design, above). `DisturbanceReadingSubmitIn` (`condition_key`, `indication`, `significant_fault`, `remarks`) and `DisturbanceResultOut`/`DisturbanceReadingRecordOut` are shared verbatim across all three record-only tests (12.1/12.2/12.4) — one contract module for three `test_type`s, not three.

`InstrumentParams` (`app/contracts/instrument.py`) — the engine-facing subset of an instrument row every test service depends on — gained three fields this task: `indication_type` (Discrimination's variant derivation, Sensitivity's applicability gate), `is_mobile` (Tilting's applicability gate), `d_value` (Discrimination's digital sub-procedure). Purely additive: every earlier consumer (Weighing, Zero-tare, Repeatability, Eccentricity) only ever read the original four fields and is unaffected.

**Decimal-as-string discipline (the critical rule).** Every numeric field uses a shared `StrictDecimal` type (`backend/app/contracts/common.py`): it accepts a JSON string (preferred) or an int, and **rejects a bare float outright** — not because pydantic's own default `Decimal` coercion is unsafe (checked: it converts a float via `str()` internally, so `300.6` doesn't silently become `300.5999...`), but because the contract layer's job is to guarantee this regardless of that implementation detail, and to keep API clients on the wire-safe path (quoted decimal strings) rather than relying on an unquoted JSON number happening to work out. On output, `model_dump(mode="json")` serializes every `Decimal` field back to a string via a `PlainSerializer` — a `Decimal` never crosses the wire as a JSON number in either direction.

**One source of truth for enums.** `WeighingReadingIn`/`WeighingResultOut` use `engine.types.AccuracyClass` and `VerificationType` directly as field types — not a mirrored copy. An API value and an engine value are the same Python object, so they cannot drift; `test_contract_enums_are_the_engine_enums_not_a_copy` locks this in. `Direction` (up/down) has no engine equivalent — the engine is direction-agnostic — so it's defined once in `common.py`.

**The engine↔contract seam is two named functions**, not scattered conversion code: `reading_to_engine_kwargs(reading: WeighingReadingIn) -> dict` (feeds `engine.weighing.compute_weighing_result`) and `result_to_out(result: WeighingResult) -> WeighingResultOut` (the reverse). `WeighingResultOut` mirrors the engine's full derivation (`L, I, delta_l, E0, E, Ec, mpe, margin, passed`) plus the MPE band context (`mpe_in_e`, `band_lower_m`, `band_upper_m`) — never just a boolean.

**`L` is a validated field, not a trusted one.** `WeighingReadingIn.L` exists on the model (system-generated from `engine.load_sequence`, per its own field description) precisely so it passes through the same validation as every other value — the contract's job is to validate shape, not to decide provenance.

The engine package remains completely untouched by this layer: `backend/app/contracts/` imports from `engine/`, never the reverse, and `tests/test_purity.py` (run in the same suite as these contract tests) confirms no Pydantic import ever leaks into `engine/`.

**Known follow-up, not solved here.** The `engine/` package lives at the repo root, outside `backend/`, which is the Vercel Services `backend` service's own root directory. Wiring these contracts into real routes will need to confirm `engine/` is actually reachable in that service's deployed bundle — a deployment detail for the task that does that wiring, not this one.

## Roles & permissions

Three roles: `technician`, `approver`, `admin`. New signups default to `technician` via `handle_new_user()`; promotion to `approver`/`admin` is seed-script-only (ADR-0004), not an admin UI.

The non-negotiable rule is separation of duties: no one both produces and approves the same result. This is enforced twice:
- **At the database**, via RLS: the `sessions_update_approver` policy requires `created_by <> auth.uid()` in addition to the approver/admin role. A technician attempting to approve their own session matches no UPDATE policy at all and the write fails with Postgres error `42501`.
- **At the API layer**, as defense in depth, independent of the RLS check.

## Session lifecycle

`draft → submitted → approved → issued`, with two additional states:
- **returned** — an approver sends a submitted session back; the technician edits it from `draft` or `returned` and resubmits.
- **superseded** — an issued report later found to be wrong is never edited in place. A new session is created referencing the original via `supersedes_session_id`; the original session remains retrievable, not deleted. (Superseding itself is not built in this task — `supersedes_session_id` exists on the schema but nothing writes to it yet.)

`issued` sessions are immutable at the database: no UPDATE policy on `test_sessions` matches a row once its status is `issued`, so no role (including admin, under the current policy set) can modify it through RLS.

**Transitions are implemented as five endpoints** (`app/routers/sessions.py`), each a thin wrapper around one `test_sessions` UPDATE plus a non-fatal `audit_log` write (`app/repositories/readings.py`'s `insert_audit_log`, reused — it's session-scoped, not readings-specific, despite the module name):
- `POST /api/sessions/{id}/submit` — creator only, `draft → submitted`, sets `submitted_at`. Rejects with 409 if the session has recorded zero readings across every test (`readings_repo.has_any_reading` — no test_type filter, spans all seven checklist tests) — nothing for an approver to review yet.
- `POST /api/sessions/{id}/reopen` — creator only, `returned → draft`. **Not one of the task's four named transitions**, but added because nothing else moves a session out of `returned`: `readings_write`'s RLS policy (db/schema.sql) requires `status = 'draft'` before any reading can be edited at all, so "the technician edits it from `draft` or `returned`" (above) is only actually possible for a `returned` session after this transition runs first. The frontend's "Reopen for editing" button (`SessionPage.jsx`) is this endpoint's only caller.
- `POST /api/sessions/{id}/return` — approver/admin only, not the session's own creator, `submitted → returned`, with a required `reason` (`SessionReturnIn`, 1–2000 chars). The reason is stored ONLY in `audit_log.data.reason` (action `'returned'`) — there is no dedicated `test_sessions` column for it (out of this task's schema-change budget) — and read back via `get_latest_return_reason` (latest `action='returned'` row for the session) whenever `SessionOut` is built for a currently-`returned` session. Deliberately the one audit write in this app that is **not** non-fatal, and written **before** the status UPDATE: since the reason has nowhere else to live, losing that write would silently discard it while the session still visibly changed status; sequencing it first means a failure leaves the session unmodified (safe to retry) rather than "returned" with its reason gone.
- `POST /api/sessions/{id}/approve` — approver/admin only, not the session's own creator, `submitted → approved`, sets `approved_by`/`approved_at`. This is the separation-of-duties action the whole task exists to demonstrate.
- `POST /api/sessions/{id}/issue` — approver/admin only, not the session's own creator, `approved → issued`, sets `issued_at` and `certificate_number` (via `issue_certificate_number()`, ADR-0008). **Who may issue, a deliberate choice:** an admin may issue any approved session; an approver may issue only the one THEY THEMSELVES approved (`ensure_can_issue`, `app/services/sessions.py`) — a different approver stepping in is treated as a separate decision from the original approval, not interchangeable with it. This is an API-layer-only rule; RLS's `sessions_update_approver` policy has no notion of "the same approver" and would permit any approver/admin (not the creator) to make this UPDATE — the API layer is strictly narrower here, which is allowed (RLS is the coarse floor, not the ceiling).

**Separation of duties, enforced twice, exactly per CLAUDE.md:**
- **At the database.** `sessions_update_owner`/`sessions_update_approver` (`db/schema.sql`) are unchanged by this task. An approver attempting to act on their own session matches neither policy (`sessions_update_owner` requires `created_by = auth.uid()`; `sessions_update_approver` requires `created_by <> auth.uid()`) — the UPDATE fails with Postgres `42501`, surfaced by `run_update` (`app/repositories/errors.py`, new this task, symmetric to `run_insert`) as a `RepositoryError(likely_rls=True)`, mapped to a 403.
- **At the API.** Every approver-only route resolves the caller's own role first (`app/repositories/profiles.py`'s `get_role` — reuses the same `profiles_select_own` RLS clause `/whoami` already relies on, `id = auth.uid()`, so this always sees the caller's own row regardless of role) and then calls `ensure_is_approver_or_admin` and `ensure_not_own_session` (`app/services/sessions.py`) BEFORE attempting any write — a technician calling `/approve`, or an approver calling it on their own session, gets a specific 403 message (`"cannot approve: separation of duties — you cannot approve a session you created yourself"`) rather than a bare RLS rejection. Both checks are pure, unit-tested directly (`backend/tests/services/test_sessions_service.py`), independent of whether the DB-level check would also have caught it.

**Invalid transitions are a clean 409, never a 500 or a bare RLS 403.** `ensure_status` (`app/services/sessions.py`) checks the session's CURRENT status against exactly what each transition requires (submit only from `draft`; return/approve only from `submitted`; issue only from `approved`; reopen only from `returned`) and raises `InvalidTransition` — caught at the router and returned as 409 with a message naming both the actual and expected status. This is deliberately NARROWER than what RLS itself would allow: `sessions_update_approver`'s `USING` clause permits `status in ('submitted','returned','approved')` for ANY approver-role UPDATE, which would technically let e.g. an `approved → returned` move through RLS — the API layer is the one place finer transition validity is actually enforced (the schema comment beside that policy already says as much: "finer transition validity ... is enforced at the API layer as defense in depth").

**`SessionOut` carries the full lifecycle trail** (`app/contracts/session.py`): `submitted_at`, `approved_by`, `approved_at`, `issued_at`, `certificate_number` (straight from the `test_sessions` row, all `None` until their transition happens) and `return_reason` (NOT a column — populated only when the session's current status is `returned`, via `get_latest_return_reason`, so every other status skips that extra read).

## API surface

The FastAPI app is mounted entirely under `/api` (an `APIRouter(prefix="/api")` in `backend/app/main.py`), so route handler code and public URL match exactly — no prefix-stripping happens at the routing layer.

Deployed as two [Vercel Services](https://vercel.com/docs/services) in one project on one domain (`/vercel.json` at the repo root): `frontend` (the Vite build, `framework: "vite"`, served at `/`) and `backend` (the FastAPI app, `entrypoint: "main:app"` — a thin shim at `backend/main.py` re-exporting the real `app` from `backend/app/main.py`, following the entrypoint convention Vercel expects at the service root). A rewrite sends `/api/:path*` to the backend service; everything else routes to the frontend service.

**SPA fallback, fourth attempt — nested `rewrites` inside `services.frontend`, the mechanism proven by real-world Vercel Services deployments.** Three prior attempts are documented failures in `docs/errors/ERROR_LOG.md`: attempt 1 (root catch-all destination `{"service": "frontend", "path": "/index.html"}`) shipped and deep links still 404'd; attempt 2 (root catch-all as the plain string `"/index.html"`) took the entire site down (no `index.html` at the project root in this multi-service layout) and was reverted; attempt 3 (a separate `frontend/vercel.json` scoping the SPA rewrite to the frontend service's own root) still 404'd on deep links after deploy — the per-service-file mechanism it bet on was never confirmed from a primary source and evidently isn't how Vercel actually resolves this for the `services` config model.

The current, working mechanism: a `rewrites` array nested as a property **inside the `services.frontend` block** of the ROOT `vercel.json` itself — not a separate file, not a `path` override on the top-level catch-all destination:
```json
"services": {
  "frontend": {
    "root": "frontend/",
    "framework": "vite",
    "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
  }
}
```
with the root-level catch-all reverted to the bare form, `{"source": "/(.*)", "destination": {"service": "frontend"}}` (no `path` key — that key was never confirmed to do anything and is dropped here). This exact shape — service-nested `rewrites`, no root-level `path` override — matches TWO independent real-world projects that hit and fixed this identical bug (Vercel Services + SPA deep-link 404s on a Vite frontend): [MACantara/Phalanx-Cyber-Academy#465](https://github.com/MACantara/Phalanx-Cyber-Academy/pull/465) (merged) and VictorBravo9er/Teacher-Assistant-Workspace#18/#19. `frontend/vercel.json` (attempt 3) is removed — it was unconfirmed and is superseded by this approach.

**Still not confirmed from Vercel's own primary docs** (`vercel.com`/`openapi.vercel.sh` remain egress-blocked from this sandbox) — this is the best-evidenced option found (two independent, real, working deployments using this exact shape, one merged), but the next deploy is still the actual test. `/api/:path*` remains first in the root `rewrites` array and is unaffected — a frontend-service-scoped rewrite can only affect requests already routed to that service.

**Getting `engine/` into the deployed backend function (ADR-0006).** Vercel builds the `backend` service from `backend/` as its root, so the sibling `engine/` package at the repo root is not part of that service's function bundle by default — the deployed function crashed at import time (`ModuleNotFoundError: No module named 'engine'`) until this was fixed. The fix: `services.backend.installCommand` in `vercel.json` runs `cp -r ../engine ./engine && pip install -r requirements.txt` — copying `engine/` into `backend/engine/` at build time, before Vercel's Python builder packages that service, then installing dependencies explicitly (this command fully replaces whatever install step would otherwise run). `backend/engine/` is gitignored — it's a build-time-generated copy, never a second source of truth; every `from engine...` import in `backend/app/` still points at the one real package. Locally, nothing changes: `uvicorn app.main:app` and the test suite still resolve `engine` from the repo root exactly as before (`backend/tests/conftest.py`'s `sys.path` insertion), so this fix is purely deploy-side. See ADR-0006 for why this approach (a build-time copy) was chosen over `includeFiles` or making `engine/` a pip-installable local package — and what remains genuinely unverified until the next real deploy.

Locally, the same mount path is used: `uvicorn app.main:app` still serves `/api/health`, `/api/whoami`, `/api/whoami/debug` on `http://localhost:8000`. CORS is same-origin (and therefore off) in production; for local dev, an env-configurable allowed origin (`CORS_ALLOW_ORIGIN`, default `http://localhost:5173`) replaces what would otherwise be a permissive wildcard.

Read-only; RLS already allows creator + approver/admin to select both tables, so no new policy was needed. Either `run_id_a`/`run_id_b` may be omitted, meaning the implicit default/only run — so a Weighing test with exactly one extra run can compare it against the original readings without those ever having been tagged with a `run_id`.
- **Damp heat (clause 13, `feat/damp-heat-endurance`)** — `POST /api/sessions/{id}/damp-heat/setup`: idempotent, creates whichever of the three FIXED runs ("a) Initial test (at reference temperature)", "b) Test at high temperature and 85% relative humidity", "c) Final test (at reference temperature)" — `app.services.damp_heat.FIXED_RUN_LABELS`) don't already exist, returns the full ordered list; a no-op once all three exist, safe to call on every page load. `GET /api/sessions/{id}/damp-heat/sequence` — mirrors `GET .../weighing/sequence` exactly (`app.services.damp_heat.build_sequence`, itself calling `engine.load_sequence.generate_load_sequence` — the SAME sequence Weighing itself generates for this instrument/verification_type, no new logic). `GET .../damp-heat/readings?run_id=` (run_id NOT optional in practice — Damp heat has no implicit default run, unlike Weighing) / `POST .../damp-heat/readings` — mirror the Weighing readings routes exactly, computed via `engine.weighing.compute_weighing_result` (no new engine), 422 if a submitted `run_id` doesn't name a `damp_heat` run belonging to this session. `GET .../damp-heat/runs/compare?run_id_a=&run_id_b=` — reused, unmodified, from `app.services.runs.compare_records`; informational only (each run's own `|Ec| <= mpe` is the real pass/fail, unlike Endurance below).
- **Endurance (clause 15, `feat/damp-heat-endurance`)** — `POST /api/sessions/{id}/endurance/setup`: same idempotent shape as Damp heat's, for its own two fixed runs ("a) Initial test", "c) Final test" — `app.services.endurance.FIXED_RUN_LABELS`). `PATCH /api/sessions/{id}/endurance/cycling` — b) Performance of the test (page 47): `EnduranceCyclingIn` (`number_of_loadings`, `load_applied`), written to the Final run's own `conditions` (ADR-0011) — the server looks up the Final run by its own fixed label (`app.services.endurance.FINAL_RUN_LABEL`) rather than the client supplying a run id, same "server derives it" discipline as everywhere else in this app; 409 if the Final run hasn't been set up yet. `GET /api/sessions/{id}/endurance/sequence`, `GET .../endurance/readings?run_id=`, `POST .../endurance/readings` — mirror Damp heat's own three routes exactly, same reasoning. `GET /api/sessions/{id}/endurance/durability` — the form's own extra column/verdict: looks up the Initial/Final runs by their own fixed labels (no query params — the server derives which two runs to compare), builds each run's reading records, and returns `DurabilityCheckOut` (`comparisons: list[RunComparisonEntryOut]`, `all_passed: bool`) via `app.services.runs.compare_records` + the NEW `app.services.runs.durability_check_from_entries` → `engine.comparison.compute_durability_check`. 409 if either run hasn't been set up yet.
- `GET /api/sessions/{id}/zero-tare/checks`, `GET .../zero-tare/readings`, `POST .../zero-tare/readings` — the zero/tare device accuracy variant, mirroring the three Weighing routes above exactly (`checks` ~ `sequence`). Stored under `test_type='weighing'` (no separate enum value — see Database schema) with `direction` always `null`, which is what `GET .../zero-tare/readings` filters on to exclude regular Weighing-sequence rows (`direction` is always set for those).
- `GET /api/sessions/{id}/repeatability/readings` — both series' current state (`L`, `mpe`, submitted readings, and — once at least one reading exists — the spread/pass-fail aggregate), always 2 entries even with zero readings submitted (an empty series is "not started," not an error). `POST /api/sessions/{id}/repeatability/readings` — submit one reading for one series; recomputes that WHOLE series (existing stored readings + this submission) via `engine.repeatability.compute_repeatability_series` and returns the up-to-date series state, not just the one reading — a series' pass/fail can't be known from a single reading in isolation. Each reading also gets its own `test_results` row (`reading_id` set, `passed` = that reading's own `|E| <= mpe`); the series-level aggregate itself is never stored, always recomputed from the stored raw `I`/`delta_l` values (`app/services/repeatability.py`) — the one place in this task's API surface where a GET recomputes rather than reads back a stored result, and deliberately so: the aggregate is inherently a function of the full, changing reading set, not a fixed value that could go stale in storage.
- `GET /api/sessions/{id}/eccentricity/setup` — the one fixed test load and its `mpe`, known before any position is submitted. `GET .../eccentricity/readings`, `POST .../eccentricity/readings` — mirror the Weighing readings routes, keyed by `position_no` (1-4) instead of `direction`; `E0` is part of the submitted body here (per-position, technician-supplied), unlike Weighing's one session-level `E0`.
- `GET /api/sessions/{id}/discrimination/checks`, `GET .../discrimination/readings`, `POST .../discrimination/readings` — the applicable sub-procedure (`variant`) is derived from the instrument's `indication_type` server-side; `POST` 422s (`MissingFieldsForVariant`) if the body is missing the field(s) that derived variant actually needs (`I1`/`I2` for analog/digital, `visible_displacement` for non-self-indicating). No applicability gate on the route itself — every indication type has a valid sub-procedure, including digital (kept N/A only at the frontend, per clause 8.3.3).
- `GET /api/sessions/{id}/sensitivity/checks`, `GET .../sensitivity/readings`, `POST .../sensitivity/readings` — `POST` 422s if the instrument's `indication_type` isn't `non_self_indicating` (clause 6.1), checked server-side, not just gated in the UI.
- `GET /api/sessions/{id}/tilting/readings` — the full current `TiltingStateOut` (L/mpe for both loaded rows, every reading submitted so far, both pass criteria), recomputed from stored readings on every call — no separate "setup" route, same reasoning as Repeatability. `POST .../tilting/readings` — 422s if `instrument.is_mobile` is false (clause 4.18); on success, fetches what's already stored, merges the new submission in LOCALLY (not a second DB read after the insert — avoids depending on read-after-write timing, and is the exact pattern `POST .../repeatability/readings` already uses), recomputes the whole state via `app.services.tilting.compute_state`, inserts the reading, and returns the up-to-date whole state. `sequence_no` encodes the phase (`0=unloaded, 1=loaded_l, 2=loaded_max` — `test_readings.sequence_no` is `not null`, so a phase needs *some* integer even though Tilting has no real "sequence" concept); `position_no` is the tilt position (1-5).
- `GET /api/sessions/{id}/voltage-variations/levels`, `GET .../voltage-variations/readings`, `POST .../voltage-variations/readings` — clause 11 (A.5.4), COMPUTED (unlike the four routes below): mirrors the Zero-tare/Sensitivity shape exactly, but at a single fixed load (10e) tested at three power-supply voltage levels (`level_key`: `reference`/`lower`/`upper`) instead of a list of check loads. `POST` reuses `engine.weighing.compute_weighing_result` directly — no new engine (`app/services/voltage_variations.py`) — and 422s if the instrument's `indication_type` is `non_self_indicating` (no electronics to power-vary).
- `GET /api/sessions/{id}/{ac-mains-dips|electrical-bursts|electrostatic-discharges}/conditions`, `GET .../readings`, `POST .../readings` — clauses 12.1/12.2/12.4, RECORD-ONLY (see "Record-only disturbance tests," below, for why there is no computation at all here). `conditions` returns that test's own fixed, predefined list (`app/services/disturbance.py`); `POST` validates the submitted `condition_key` against it (422 if unknown) and the same non-self-indicating 422 gate as Voltage variations, then stores the technician's `indication`/`significant_fault`/`remarks` observation verbatim — `passed = not significant_fault` (forced `false`, server-side, for a "without disturbance" baseline row regardless of what the client sends, since the form itself has no fault check on those rows). All three routes share ONE implementation (`_get_disturbance_conditions`/`_list_disturbance_readings`/`_submit_disturbance_reading` in `app/routers/sessions.py`) parameterized by `test_type` — not three near-identical copies.
- `POST /api/sessions/{id}/report` — generates and returns the certificate PDF for an ISSUED session (approver/admin or the session's own creator; 409 if not yet issued), stores it in Supabase Storage, and records the storage path (PDF & audit, below).
- `GET /api/verify/{certificate_number}` — PUBLIC, no auth at all. Returns a fixed safe field list for an issued certificate, or a 404 indistinguishable between "never existed" and "exists but not issued" (PDF & audit, below; ADR-0009).
- `POST /api/verify/{certificate_number}/report-discrepancy` — PUBLIC, no auth at all. Records a free-text discrepancy report against a certificate number, no existence check (PDF & audit, below).

**Record-only disturbance tests (`feat/disturbance-test-forms`) — a genuinely different category from every other test in this app.** Clause 12.x (electrical disturbances: AC mains voltage dips, electrical bursts, surges, electrostatic discharges, radiated/conducted EM immunity, road-vehicle transients) requires physical EMC test equipment — a disturbance generator, an ESD gun, an antenna, a battery-transient simulator — that no software can drive or measure. R 76-2's own pass rule for every one of these forms is literally "check if a significant fault occurred": the TECHNICIAN, standing at the bench, compares the instrument's post-disturbance indication against its pre-disturbance one (or watches for the instrument's own fault-detection to trigger) and judges whether the difference exceeds `e`. There is nothing here for an engine to compute — so, deliberately, none of the four record-only tests built this task (`ac_mains_dips`/`electrical_bursts`/`electrostatic_discharges`, clauses 12.1/12.2/12.4) HAS an engine module; `app/contracts/disturbance.py`'s module docstring has the full reasoning. The API's only job for these three is validating that a submitted `condition_key` is one of that test's own fixed, predefined condition list (read from the OIML form itself, `pdftoppm`-rendered — pages 24/25/29 respectively) and storing the technician's observation (`indication`, `significant_fault`, `remarks`) verbatim; `passed` is a trivial `not significant_fault`, computed at the API layer, not an engine.
- **Voltage variations (clause 11, A.5.4) is the one exception — it DOES compute**, because it's a Weighing-formula application, not a disturbance-immunity check: A.5.4 varies the instrument's power-supply voltage (reference/lower/upper) and re-checks the SAME `E = I + ½e − ΔL − L`, `Ec = E − E0`, `|Ec| ≤ mpe` criterion Weighing already uses, at a small fixed load (10e). `app/services/voltage_variations.py` calls `engine.weighing.compute_weighing_result` directly — no new engine, same reasoning `app/services/zero_tare.py` already established for the same formula at different check loads.
- **What was built vs. deferred, and why.** Given the size of all eight clause-11/12.x forms, this task prioritized the four most commonly performed in practice: 11 (Voltage variations), 12.1 (AC mains dips), 12.2 (Electrical bursts), 12.4 (Electrostatic discharges). Surges (12.3), radiated EM immunity (12.5), conducted RF immunity (12.6), and road-vehicle transients (12.7) are real OIML clauses this app has NOT built — no contract, no service, no route, no form, no `test_type` enum value for any of them. They remain "Not implemented" on the page-9 summary (`summaryChecklist.js`, unchanged placeholders) exactly like every other not-yet-built clause. Building one later follows the same pattern this task established for the other four: a condition list in `app/services/disturbance.py` (read from its own OIML page), a `test_type` enum value (another additive `ALTER TYPE ... ADD VALUE` migration), and a `DisturbanceFormTable`/`createDisturbanceSessionPage` call site on the frontend (see Frontend, below) — no new architecture needed.
- **Two documented simplifications, not silently dropped.** (1) 12.2(b) "I/O circuits and communication lines" has 9 blank, generically-numbered cable/interface slots on the real form (a technician fills in however many are actually connected) — this app fixes it at 3 slots, since "N generic slots" doesn't fit the fixed-condition-list model every other test here uses; a session needing more than 3 records the rest in the free-text Remarks field. (2) Voltage variations' own form prints TWO near-identical 3-level tables ("if an instrument has more than one power supply") and two unlabeled blank rows per level within each — this app builds one category/table with one row per level, same "blank paper form" convention Eccentricity's mobile-instrument pre-question already used for an unmodeled part of a source form.

Every route EXCEPT the two public `/verify/...` ones (above) depends on `app.deps.get_auth_context` (`Depends(get_auth_context)`) — one reusable dependency that extracts the caller's JWT, builds the per-request user-scoped client (`app.supabase_client.user_client`), and resolves `auth.uid()` via GoTrue's `get_user(jwt)` so a route needing it for an insert payload (`registered_by`, `created_by`, `entered_by`, `actor_id`) never has to re-derive it. There is still no service-role client anywhere in `backend/` — the public verify routes use `app.supabase_client.anon_client()` instead (pre-existing, unused before this task), a narrow, deliberate exception (ADR-0009), never service-role.

**Server-derives-L.** The technician never enters or sees a raw `L` value as something they typed — `GET .../weighing/sequence` calls `engine.load_sequence.generate_load_sequence` with the session's instrument params and returns each entry's `sequence_no` (its stable index), `L`, `m`, `kind`, and `mpe`. `POST .../weighing/readings` takes only `sequence_no`, `I`, `delta_l`, `direction`, `E0` from the client (`WeighingReadingSubmitIn` — deliberately narrower than the engine-ready `WeighingReadingIn`), regenerates the *same* sequence server-side, and looks up `L` for that `sequence_no`. Both routes call `app.services.weighing.build_sequence` — the one place `generate_load_sequence` is invoked from the API layer — so they can never disagree about what a given `sequence_no` means. Deterministic, so nothing about the sequence is stored; it's recomputed on every call.

**Reading + result, written together.** supabase-py/PostgREST has no client-side multi-table transaction. The chosen approach: insert the reading, then insert the result; if the result insert fails, delete the just-inserted reading rather than leave one with no computed verdict (`app/routers/sessions.py`, `submit_weighing_reading`). A single Postgres RPC doing both inserts atomically would remove this rollback step entirely — a reasonable follow-up, not built in this task.

**Readings only while `draft`** (`app.services.sessions.ensure_session_is_draft`) — a 409 otherwise. This deliberately only enforces that one rule; the `returned → draft` reopening and the `submitted`/`approved`/`issued` transitions are a later task's concern, and nothing here blocks building that later.

**Audit is non-fatal.** On reading submission, an `audit_log` row is inserted (`action='weighing_reading_submitted'`); if that insert fails, a warning is logged and the request still returns success (docs/plan.md: "audit writes non-fatal but surfaced"). No hash chain (stretch/out of scope, ADR-0005).

**Two Decimal policies, deliberately different, at two different boundaries.** `StrictDecimal` (`app.contracts.common`) governs untrusted CLIENT input and rejects a bare float outright. Supabase/PostgREST returns `numeric` columns as JSON numbers (Python `float`) on every read — a completely different, trusted boundary — so `app.db_decimal.decimal_from_db_value` converts those via `Decimal(str(value))` (safe: Python's float repr is shortest-round-trip) before a DB row ever reaches an `Out` contract's `StrictDecimal` field. Passing a raw DB-row float straight into a `StrictDecimal` field would incorrectly trip the client-input rejection on every normal read — `instrument_out_from_row`/`instrument_params_from_row` (`app.contracts.instrument`) exist specifically to do this conversion first.

**Errors are typed, not raw 500s:** missing/invalid body → 422 (Pydantic, automatic); malformed `instrument_id` in a `POST /sessions` body → 422 (`SessionIn.instrument_id` is `pydantic.UUID4`, see below); session not `draft` when submitting a reading → 409; `sequence_no` out of range → 422; instrument/session not found, not visible under RLS, *or* not resolvable as an id at all → 404 (deliberately not distinguished — CLAUDE.md: RLS fails silently, and a caller shouldn't be able to probe for the existence of another user's row either way).

**Hardened DB-error handling (fix for a real production 500) — `app.repositories.errors`.** `POST /api/sessions` was 500ing in production. Diagnosis (code-only, no live DB access): `repositories/sessions.py`'s `insert_session`/`insert_session_test_selection` did `rows = client.table(...).insert(...).execute().data; return rows[0]` with no guard — a bare `IndexError` on empty `rows`, and no `try/except` around the PostgREST call at all, so an outright `postgrest.exceptions.APIError` (an RLS `WITH CHECK` rejection, a malformed id hitting `invalid input syntax for type uuid`, ...) was equally unhandled. Both are the two failure shapes CLAUDE.md's own guardrail names ("RLS fails silently ... handle both failure shapes: explicit error vs. empty result") — this code did neither. Fixed systemically, not just patched at the one call site:
- **`app/repositories/errors.py`** (new) — `RepositoryError(table, operation, hint, likely_rls)`, and two helpers every repository write/read now goes through instead of a bare `.execute().data`: `run_select` (an empty result is a normal SELECT outcome, returned as-is; only an outright `APIError` — malformed id, genuine RLS rejection — becomes a `RepositoryError`) and `run_insert` (wraps `APIError` *and* guards the empty-`rows` case, so `rows[0]` never throws unguarded again). `likely_rls` is set from the Postgres error code (`42501`/`PGRST301`) or, for the empty-insert-result case, always true (that shape *is* RLS's silent-failure mode). Applied to every insert/select helper in `repositories/instruments.py`, `sessions.py`, `readings.py` (not `delete_reading`/`insert_audit_log` — neither does `rows[0]`, and the audit write is deliberately non-fatal already).
- **Two response shapes for `RepositoryError`, deliberately different.** For the "resolve a path-param id" step (`_get_instrument_or_404`/`_get_session_or_404` in `routers/sessions.py`, and the equivalent in `routers/instruments.py`) a `RepositoryError` folds into the *same* 404 a genuinely missing/not-visible resource gets — a malformed id fits the existing "can't resolve to anything the caller may act on" bucket, not a new status code — but the `detail` still carries the underlying PostgREST error, so it's diagnosable, not silent. For a write (`create_session`'s two-step insert, `submit_weighing_reading`'s reading/result inserts, `create_instrument`), a local `try/except RepositoryError` maps `likely_rls` to 403, anything else to 500, with `detail` naming which table/operation failed and why. **`app/main.py` registers a global `@app.exception_handler(RepositoryError)`** as the systemic backstop for every route that doesn't have its own local catch (most GETs) — the same 403/500-by-`likely_rls` mapping, so a `RepositoryError` can never again reach FastAPI's default handling and come back as an opaque, detail-free 500.
- **`SessionIn.instrument_id` is `pydantic.UUID4`, not a bare `str`** (`contracts/session.py`) — the frontend-bug shape (empty string, the literal `"undefined"`/`"null"`, any non-UUID garbage) now fails Pydantic validation as a clean 422 before any DB call, rather than reaching Postgres and 500ing on `invalid input syntax for type uuid`. `instruments.id` is `gen_random_uuid()` (pgcrypto) — always a v4 UUID — so `UUID4` (not the looser `UUID`) is the correct, exact type. Path-param ids (`session_id`, `instrument_id` in URLs) are deliberately *not* given the same contract-level treatment in this task — narrower scope, and the 404-folding above already makes a malformed path-param id diagnosable rather than a bare crash, just not a 422.
- **Backend test coverage added, not just the fix:** `backend/tests/repositories/test_errors.py` (pure unit tests — `run_select`/`run_insert` against a fake query object, proving both failure shapes raise `RepositoryError` and never a bare `IndexError`/`APIError`), plus new `backend/tests/routers/test_sessions_router.py` cases for `POST /sessions` (previously **completely untested** — the exact endpoint that was 500ing in production had zero router-level coverage): happy path, instrument-not-found → 404, malformed `instrument_id` → 422, a `RepositoryError` from either insert step → 403/500 with an informative `detail`, and a malformed `session_id` on a GET → 404 not 500. Equivalent malformed-id/`RepositoryError`-mapping cases were added to `test_instruments_router.py`.

**Resolved:** `engine/` living outside `backend/`'s own Vercel-service root (flagged when the Weighing contracts were added) did in fact break the deployed function, exactly as flagged — see "Getting `engine/` into the deployed backend function" above and ADR-0006 for the fix. Also resolved this task: the `POST /api/sessions` 500 described above.

**Testing note.** This sandbox has no egress to a live Supabase project. The pure logic — contract validation, the engine↔contract adapters, the `sequence_no → L` lookup, the not-draft rule — is unit-tested directly (`backend/tests/services/`, `backend/tests/contracts/`). The routes themselves are tested with the entire DB layer mocked (`backend/tests/routers/`) via `app.dependency_overrides` (for auth) and `monkeypatch` (for `app.repositories.*`) — this proves the routing/error-code/orchestration logic, not that the real SQL against the real schema behaves as expected. That needs the preview deploy (see SESSION_LOG.md for the verification steps).

## Frontend

**Stack.** Vite + React (already in place), now with Tailwind CSS v4 (`@tailwindcss/vite`, CSS-first config — no `tailwind.config.js`) and shadcn/ui, `react-router-dom` for routing, `react-hook-form` for forms, and `sonner` for toasts. `ui.shadcn.com` is unreachable from this sandbox (egress-blocked, same as `vercel.com`), so the shadcn CLI (`init`/`add`) could not be run; the `components/ui/*.jsx` files were written by hand to shadcn's own standard shape (same props, same class names, same `cn()`-based composition) so a future `npx shadcn add <component>` in an environment with network access still targets the same structure without conflicting. `components.json` is committed for that reason even though it was never used to generate anything here.

**Design tokens** (`src/index.css`, `@theme inline`) — one deliberate choice per rule, each changeable in one place: a restrained deep slate-blue `--primary` (official/regulatory, not a startup gradient); slate-based (cool) neutrals for `--background`/`--muted`/`--border`; a small `--radius` (6px, closer to a form than a consumer app); semantic `--success`/`--warning`/`--destructive` tokens kept separate from `--primary` so a pass/fail/pending badge is never visually confused with a call-to-action button; Tailwind's default system sans stack for typography (no external font fetch, so no added network dependency). No dark mode yet — a second `.dark` block is the only change needed to add one later.

**App shell — left sidebar, not a top bar** (`src/components/AppShell.jsx`) — the layout every authenticated screen renders inside EXCEPT the seven test-entry screens (see "Focused test-entry mode," below, which use the sibling `FocusedShell` from the same file instead): a persistent left sidebar (wordmark, role-driven nav, and a bottom-pinned identity block — email, role badge, log out) plus a main content area, via a nested `<Outlet/>` route. Replaced the earlier top-bar nav (same component, same route wiring) specifically so a longer, role-varying nav list has room to grow without crowding a single horizontal row. `PageHeader` (same file) is unchanged — the consistent title-area component every screen starts with. Responsive: at `md` and above the sidebar (`<aside>`) is always visible; below `md` it becomes a hamburger-triggered drawer over a backdrop (both the backdrop and the drawer are `md:hidden`, so neither ever renders at desktop widths) — chosen over letting the same nav try to fit a narrow top bar, which would either wrap unpredictably or need its own overflow menu.

**Role-driven nav, not disabled-but-visible** (`src/lib/navigation.js`, `navItemsForRole(role)`) — the sidebar's single source of truth for "which items exist for this role," reused nowhere else yet but written as its own module specifically so it CAN be reused (e.g. a future mobile nav) without redefining the list. An item a role can't act on is filtered OUT of the array returned to that role, not rendered disabled/greyed — a technician's sidebar literally contains no DOM node for "Sessions (all)," "Discrepancy reports," or "Audit trail." Technician: Dashboard, Instruments, My sessions. Approver: Dashboard, Instruments, Sessions (all), Discrepancy reports, Audit trail. Admin: the approver's list, unchanged — **no "Users & roles" item**, deliberately: that page doesn't exist (role promotion is still seed-script-only, ADR-0004), and the guardrail here is "never link to a 404," so `navigation.js` carries only a comment noting where to add it, gated to `["admin"]`, the day that page is built — not a commented-out entry. An unrecognized/`null` role (no visible `profiles` row — RLS returning zero rows is a valid outcome per CLAUDE.md, not an error) falls back to the technician-shared subset rather than guessing, so an edge case never accidentally grants approver-only items.

**Discrepancy reports and Audit trail are minimal placeholder pages, not omitted items.** Both `discrepancy_reports` (writes-only: the public `POST /verify/{cert}/report-discrepancy`) and `audit_log` (written on every lifecycle transition, `readings_repo.insert_audit_log`) have NO read endpoint exposed to an authenticated caller yet — this was a frontend-only task, so none was added. Rather than omitting the sidebar items (which would misrepresent the role model these two items are part of) or linking them to a route with nothing behind it, `DiscrepancyReportsPage.jsx`/`AuditTrailPage.jsx` are real routed pages that say plainly what's missing and why ("no read endpoint yet") — a "Coming soon" that explains itself, not a bare placeholder.

**Dashboard — role-aware "what needs my attention," not a generic welcome screen** (`src/pages/DashboardPage.jsx`). Technician: quick actions (Register instrument; Start verification — links to `/instruments` to pick one first, since a session can't be created without an `instrument_id`), three counts (instruments registered, sessions in progress, certificates issued — all computed client-side, see the endpoint-gap note below), and a "Needs your attention" list of their own `draft`/`returned` sessions, returned ones sorted first and shown with their `return_reason` inline (same amber treatment `SessionLifecyclePanel` already uses for it). Approver/admin (admin reuses the approver view unchanged, per this task's scope): two clearly separated sections — "Awaiting your approval" (sessions with `status === "submitted"` and `created_by !== me`, the actual work queue) and "Your own sessions" (sessions this approver created themselves), the second captioned with the separation-of-duties rule in plain text ("You cannot approve these yourself...") rather than leaving the absence of an Approve button unexplained. Counts: pending approvals, certificates issued (system-wide, since RLS already gives an approver every session). Discrepancy-report counts are explicitly NOT shown (same missing-read-endpoint gap as the placeholder page above) — a one-line note says so rather than the count silently reading zero. Empty states (`EmptyState`, same file) use a dashed-border card with real sentence, not a bare blank area — "Nothing awaiting your approval right now" is meant to read as confirmed-empty, not broken.

**The `GET /api/sessions` gap — composed client-side, not solved here** (`src/hooks/useAllSessions.js`). There is no role-scoped "list every session I can see" endpoint. The dashboard and the new `/sessions` page (below) both need exactly that, so `useAllSessions()` composes it from two endpoints that already exist: `GET /api/instruments` (RLS: every authenticated user sees every instrument — `instruments_select_auth`, db/schema.sql) followed by `GET /api/instruments/{id}/sessions` for each one (RLS: a technician sees only their own sessions there, an approver/admin sees all — `sessions_select`). This is CORRECT today — RLS already scopes each per-instrument call exactly right for the caller's role — but it is `O(instruments)` requests, not one, and will not scale past a small instrument count. **The clean fix, not built in this frontend-only task, is a real `GET /api/sessions` backend route** that expresses "sessions visible to me" directly and lets this hook collapse to a single call.

**One page behind two sidebar labels** (`src/pages/SessionsListPage.jsx`, route `/sessions`) — a technician's "My sessions" and an approver/admin's "Sessions (all)" both route to the same component; only the title/description and an extra "Created by" column differ, driven by role, because the underlying `useAllSessions()` data is already correctly scoped either way. Avoids building two near-identical list pages for what RLS already makes the same query.

**Auth** (`src/lib/supabase.js`, `src/components/AuthGate.jsx`) — a single Supabase client module; `useSession()` is a reactive hook over `getSession()` + `onAuthStateChange` (login, logout, and token refresh all flow through the same state). `AuthGate` is a layout route: `session === undefined` (initial check still in flight) renders a loading skeleton — never a redirect flash; `null` redirects to `/login`; otherwise renders the gated routes. The login screen itself uses `signInWithPassword` and shows Supabase's own error message on failure.

**API helper** (`src/lib/api.js`, `apiFetch`) — every `/api` call goes through this one function, which reads the current session and attaches `Authorization: Bearer <access_token>` automatically; callers never thread a token through by hand. Same-origin `/api` by default (matching the backend's own mount path), overridable via `VITE_API_BASE` for local dev exactly as the walking skeleton already established.

**Decimal-as-string on the client, carrying the backend's rule forward.** The backend's `StrictDecimal` contract (see above) rejects a bare float outright. On the client this means every numeric form field (`e_value`, `d_value`, `max_capacity`, `min_capacity`) is kept as the string value react-hook-form already holds it as, from the input all the way to the `fetch` body — `Number()`/`parseFloat()` never appears in `InstrumentRegisterPage.jsx`'s submit handler, by design, with a comment at the call site saying why. `apiFetch` itself does no coercion either; it only serializes whatever shape it's handed, so the discipline has to hold at each call site, not inside a shared helper that could silently paper over a mistake.

**Display rounding is presentation-only, never storage.** The engine/backend intentionally return the full-precision Decimal (e.g. a genuine repeating decimal like `1.2857142857142857143` from a load-fraction division) — no calculated verdict is trusted until the boundary-value tests pass, so the stored/computed value must stay exact. `src/lib/displayFormat.js` (`roundForDisplay(value, decimals=2)`, `roundLoadForDisplay` = `roundForDisplay(value, 1)`) is the one shared helper every test form (`WeighingFormTable`, `ZeroTareFormTable`, `RepeatabilityFormTable`, `EccentricityFormTable`, `DiscriminationFormTable`, `SensitivityFormTable`, `TiltingFormTable`) uses to round a computed result (`E`, `Ec`, `mpe`, margin/spread/difference/threshold/extra-load figures) or a derived load (`L`) at the moment it is rendered as text — using `Number()`/`toFixed()` safely specifically because the output is thrown away after rendering, never fed back into a request or component state used for submission. Identity/text fields (`application_no`, `type_designation`) and the instrument's own registered `e_value`/resolution are left unrounded — they are not computation results. This never touches the Decimal-as-string discipline above: the exact string the backend returns is still what stays in state and what gets POSTed back.

**Instrument Registration.** `/instruments` lists the caller's instruments (`GET /api/instruments`) in a shadcn `Table`, with three distinct states — loading (skeleton), empty (a message + link, not just a blank table), and error (an inline retry card, not a silent failure) — the pattern every following list screen copies.

**`/instruments/new` is a faithful reproduction of OIML R 76-2's page-6 "General information concerning the type" form** (`InstrumentRegisterPage.jsx`) — the registration-screen equivalent of `WeighingFormTable`'s page-10 reproduction, built the same way: page 6 was read as a rendered image (`pdftoppm`) and the component matches its layout — a bordered white document sheet (`max-w-4xl`, `font-serif`, black rules), not app-styled inputs — rather than a generic form with the same fields. `FormLine` (dotted fill-in line), `FormBox` (bordered "Label = [box]" numeric field), and `FormCheckbox` (☐-style tick box) were extracted out of `WeighingFormTable.jsx` into a shared `src/components/oiml/FormPrimitives.jsx` so both OIML-form screens stay pixel-identical by construction rather than duplicating the same visual primitives twice. This is fidelity to the FORM'S LAYOUT for data-entry purposes, not a copy of the copyrighted OIML document itself — no OIML explanatory/normative text beyond the form's own field labels and structural chrome.
- **Top to bottom:** the identity block (Application no. / Type designation / Manufacturer / Applicant / Instrument category, plus Model/Serial number — not on page 6 itself but kept since the app already depends on them for instrument identity); the Complete-instrument/Module line; the four accuracy-class boxes; the self-/semi-/non-self-indicating tick-boxes (mapped onto the pre-existing `indication_type` enum — no new column, only the labels changed to the form's own wording); Min/e/Max/d/n plus three blank multi-interval e1/Max1/d1/n1 rows; the T=+/− temperature inputs; the five-field power-supply line (`U`/`Umin`/`Umax`/`f`/battery `U`); zero-setting-device and tare-device tick-box columns (including "Combined zero/tare device" as a third selectable value folded into `tare_device_type`, not a fourth column); initial-zero-setting-range plus a read-only temperature-range summary of the same T=+/− values; printer tick-boxes; and a two-column bottom block for identification/software/interfaces/load-cell fields.
- **"Blank paper form" for fields with no schema column.** Several real page-6 fields (module/error-fraction testing, the three multi-interval sub-rows, "Instrument submitted," "Connected equipment," "Evaluation period," "Date of report," "Observer," "Remarks") have no backing column and are rendered as inert, blank `FormLine`/`FormBox`/`FormCheckbox` elements — full layout fidelity, exactly what an unfilled paper form looks like, never a misleadingly-interactive disabled input.
- Submits to `POST /api/instruments`; on success it toasts and navigates back to the list, on a 422 it renders the Pydantic validation detail inline, readably (both the standard Pydantic array-of-issues shape and this screen's own plain-string 422 `detail` — a classification rejection or ambiguity message — are handled). Every page-6 numeric/text field is optional and sent as `null` when blank, not an empty string.

**Accuracy class: derived, not chosen.** The old free-choice `<Select>` is gone; on this form the derived class is shown as an auto-ticked box among the form's own four accuracy-class ovals (I / II / III / IIII) rather than a badge. As the technician fills in `e`, `Max`, and `Min` (`Min` is required — Table 3 classification needs it), a live preview computes the class via `src/lib/accuracyClass.js` — a client-side MIRROR of `engine/classification.py`, kept in exact sync by hand (same six Table 3 rows, same `e`-format rule, same `d < e ≤ 10d` check), using string/BigInt-based decimal arithmetic throughout, never `Number()`/`parseFloat()`, for the same reason the rest of the app avoids float on numeric fields. Three states:
- **Exactly one class qualifies** — that class's box is auto-ticked and read-only, with "Derived from e / Max / Min (OIML R76-1 Table 3) — never chosen freely. n = 6000." shown below. Submit sends no `accuracy_class` at all; the server derives it independently and that's what's actually stored.
- **Zero classes qualify** — every box stays unticked; the engine's own rejection reason (e.g. "No accuracy class fits e=1g, Max=15000g (n=15000), Min=10g: ...") is shown inline in red, submit disabled.
- **More than one class qualifies** — ONLY the qualifying boxes become clickable (the others stay inert) so the technician ticks one among them; submit stays disabled until they do. The ticked value is sent as `accuracy_class` — purely a disambiguation hint the server re-checks against its own qualifying set, never trusted outright (`app/services/instruments.py`).
- **The server is the actual source of truth.** The client-side mirror only exists for instant feedback while typing; the real `POST /api/instruments` call re-derives the class itself from the submitted values regardless of what the preview showed, so a bug in the JS mirror could only ever produce a momentarily-wrong preview, never a wrongly-classified stored instrument.

**Navigation: Instruments → Instrument detail → Session overview → Add test → test page.** `/instruments` (list) → click a row's "View" → `/instruments/:id` (`InstrumentDetailPage`) → `/sessions/:id` (`SessionPage`, the session overview) → "Add test" (`AddTestDialog`) → pick a test → that test's own route — all seven now exist: `/sessions/:id/weighing`, `/zero-tare`, `/repeatability`, `/eccentricity`, `/discrimination`, `/sensitivity`, `/tilting` (`TEST_ROWS[*].route(sessionId)`, `src/lib/testChecklist.js`). The `verification_type` choice happens exactly once, at session creation (`StartVerificationDialog`, triggered from the instrument-detail page's "New verification session" action — renamed from "Start verification" this task, specifically to keep "session" and "test" from reading as the same thing now that a session can hold several tests) — opening a test page never asks it again.
- **Tests are technician-selectable, in ANY order — confirmed, not assumed.** RRSL (Deputy Director Sharma) confirmed there is no fixed sequence between the seven checklist tests, consistent with `docs/plan.md`'s per-session-test-selector requirement ("Tests run in any order"). No test's availability may ever depend on another test's status (not-started/in-progress/complete) — `isSelectable` (`src/lib/testChecklist.js`) takes only the row and the instrument as arguments, never session/reading/progress state, so a sequence dependency can't be reintroduced without changing that signature. Only two gates are legitimate, and neither is a sequence lock: (1) **applicability** — Discrimination N/A for digital, Tilting mobile-only, Sensitivity non-self-indicating-only, driven purely by the instrument's own properties; (2) **not yet implemented** — only Weighing has a working form, so the other six show "Coming soon" (an implementation gap, never phrased as "complete X first"). A test's displayed status (Not started / In progress / Complete) is informational only and never disables another test or the Add-test picker's other rows. This applies equally at the backend: the only status check on the session/test flow is `app.services.sessions.ensure_session_is_draft` (session-level — readings are rejected once a session leaves `draft`), which is a lifecycle gate, not a cross-test ordering rule; no endpoint conditions one test's availability on another's completion.
- **`InstrumentDetailPage`** (`/instruments/:id`) — the instrument's header info plus its verification sessions (`GET /api/instruments/{id}/sessions`): verification type, status badge, start date, an "Open" link to that session's overview. Empty state prompts to create one via `StartVerificationDialog` (unchanged mechanics: `POST /api/sessions`, then routes to the new session's overview).
- **`SessionPage`** (`/sessions/:id`) — the session overview: a breadcrumb back to the instrument, a summary header card (instrument, class/e/Max, status, verification type), an "Add test" button (`AddTestDialog`) in the page actions, `SessionLifecyclePanel` (submit/approve/return/issue, certificate number — unchanged by `feat/oiml-summary-overview`), and, as its centerpiece, `SessionSummaryTable` (below) — a faithful reproduction of OIML R 76-2's page-9 "Summary of type evaluation" master checklist, replacing the earlier ad hoc seven-row app-styled table. Status is still derived purely from what's actually been submitted — `computeProgress(total, completedCount, allPassed)`, a small shared helper: Weighing's `total` is `sequence.length × 2` (both directions); Zero-tare's/Discrimination's/Sensitivity's is each their own check-list length; Repeatability's is the fixed 20 (10 × 2 series, `allPassed` requires both series' own `passed` true); Eccentricity's is 4; Tilting's is the fixed 15 (3 phases × 5 positions, `allPassed` is the server's own `TiltingStateOut.passed`) — none of this needs a `session_test_selection` row (only Weighing has one, created unconditionally at session creation; every other test has none and doesn't need one for its status to work) — `PROGRESS_BY_KEY` is computed exactly as before and simply handed to `SessionSummaryTable` now instead of being rendered inline.
- **`SessionSummaryTable`** (`src/components/session/SessionSummaryTable.jsx`, row data in `src/lib/summaryChecklist.js`) — page 9 of R 76-2 ("Summary of type evaluation," the master ~18-clause checklist with Report page / PASSED / FAILED / Remarks columns) was read as a rendered image (`pdftoppm`, the same method used for every other OIML-form component) and reproduced with its exact numbering and row grouping: clause 1's own Initial + six °C sub-rows, clause 7's Printing-storage/Zero-setting-tare-balancing sub-rows, and every a)/b)/c) sub-row under 12.2/12.3/12.4/12.7/13/15, down to the "EXAMINATIONS" section header before 16/17. This is a faithful reproduction of the FORM'S LAYOUT for data-entry fidelity, not a copy of the copyrighted OIML document itself — no OIML explanatory text beyond the form's own row labels and structural chrome. Every leaf row is exactly one of three states, and the three are never visually or textually conflated:
  - **Implemented + applicable** (one of this app's seven checklist tests, `testChecklist.js`'s `TEST_ROWS`, and the instrument doesn't exclude it) — the row's own label is a `Link` to that test's route, clickable regardless of not-started/in-progress/complete (no forced sequence, unchanged); PASSED/FAILED render as real `FormCheckbox` ticks driven by the exact same `progressByKey` shape `SessionPage` has always computed (`computeProgress`, unchanged) — no new status logic, only a different table to render it into. Not-started/in-progress show as plain text in the Remarks cell (both ticks blank) rather than a badge, matching the paper form's own vocabulary.
  - **N/A** (the same `TEST_ROWS[*].naReason(instrument)` check `SessionPage`/`AddTestDialog` already use — Discrimination for digital, Tilting for non-mobile, Sensitivity for other-than-non-self-indicating) — plain (non-clickable) label text, and Report page/PASSED/FAILED render the form's own "– –" not-applicable convention, with the reason in Remarks.
  - **Not implemented** (every other page-9 clause — CLAUDE.md scopes this app to the 8.3.3 seven-item checklist; "Creep and the other full-battery tests are stretch/out-of-scope") — greyed label and cells, Report page/PASSED/FAILED show "—", Remarks says "Not implemented" in small italic text, never clickable. Deliberately never phrased or styled like "Not started": that phrase means an IMPLEMENTED test with no data yet, a materially different and more hopeful claim than "this app has no engine or form for this clause at all." This is the honesty distinction the task itself called for.
  - **One deliberate deviation from the printed form:** page 9 has no line for "Zero/tare device accuracy" — CLAUDE.md groups it under clause 1 ("Weighing (incl. zero/tare device accuracy)"), since both share A.4.4, but this app tracks them as two separate tests (separate routes, separate submitted data, separate forms — `ZeroTareFormTable.jsx`). Cramming two different tests' verdicts into the form's single "Initial" line would be confusing (one line, two different pass/fail ticks); inventing a same-looking NUMBERED row the real form doesn't have would misrepresent it as part of the OIML original. Instead, an extra sub-row is appended under clause 1's own group (`appAddition: true`, `summaryChecklist.js`), visually flagged (a light amber tint, an inline "(app addition — A.4.4 variant, not on the printed form)" note) as this app's own addition rather than the form's.
  - **Usable at ~720px height without dominating the page.** This page still lives in `AppShell` (sidebar visible, normal page scroll — `feat/oiml-summary-overview` did not move it into `FocusedShell`, since an overview/browsing screen isn't the sidebar-free workstation that layout is for). The ~40-row table itself gets `max-h-[60vh] overflow-y-auto` with a `sticky top-0` thead on its own wrapper — the same internal-scroll-region pattern `fix/vertical-fit-no-page-scroll` established for the Weighing table — so scrolling the checklist doesn't push the breadcrumb, summary card, or lifecycle panel out of view; this is a narrower fix than that task's full height-constrained/no-page-scroll treatment, appropriate to a browsing page rather than a data-entry workstation.
  - A bottom free-text "Remarks:" box, matching the form's own, is local component state only — same known gap as every other OIML form here (no session-update endpoint yet).
- **`AddTestDialog`** (`src/components/session/AddTestDialog.jsx`) — the "pick from the 7" surface: a dialog listing the OIML clause 8.3.3 checklist (`TEST_ROWS`, shared with the overview via `src/lib/testChecklist.js` so the two can't drift), each row greyed/disabled unless selectable. All seven now have a `route`; Weighing/Zero-tare/Repeatability/Eccentricity are universal (no applicability gate at all); Discrimination/Tilting/Sensitivity show their N/A reason when inapplicable (digital / non-mobile / other-than-non-self-indicating respectively) and are selectable otherwise — the "Coming soon" branch this component still renders for a non-selectable, non-N/A row is unreachable now that every checklist row has a form, kept only for the day a new row is added without one yet. - **Pass order — the full increasing pass, then the full decreasing pass in reverse, never "load N up, load N down."** Fixed a real domain bug (production feedback): the original walk visited `load1↓, load1↑, load2↓, load2↑, …`, which implies adding and removing weights at every single load — not how the test is actually run. For 10 loads that's the 20-field order `load1↓, load2↓, … load10↓, load10↑, load9↑, … load1↑` (each "field" being both Indication and ΔL, so 40 flat stops total). The progress line reflects the pass explicitly — "**Increasing pass** · Load 5 of 10 (↓ increasing)" then "**Decreasing pass** · Load 10 of 10 (↑ decreasing)" — so the technician always knows which physical direction they're in, not just which load.
- **Keyboard flow, unchanged in mechanism, now walking the corrected order.** Enter commits the current field and advances: Indication → ΔL (no submit yet) → Enter again submits (`POST .../weighing/readings`) and advances to the NEXT STOP IN THE PASS ORDER above (the next load in the same pass, or — only at the pass boundary, load N's ΔL where N is the last/first load — the first stop of the other pass) — driven by the one shared `buildGuidedWalkPositions` list, used by both the auto-advance-on-submit path and the explicit Previous/Next buttons, so Previous walks back along the exact same corrected path (never "the other direction of the same load"). On mount, the panel resumes at the first not-yet-submitted direction IN PASS ORDER (`findFirstIncomplete`, rewritten to walk `buildGuidedWalkPositions` rather than the old per-load order) rather than always restarting at load 1.
- **Focus management and table coexistence, made precise via a `cursor.source` flag.** `cursor` (`{sequenceNo, apiDirection, field}`) is lifted into `WeighingFormTable` and shared with the panel as props — clicking a table cell (`onFocus`) sets it too, tagged `source: "table"`. **Auto-scaling the Weighing table (`fix/autoscale-test-table`) — "fit, not fill."** Production feedback: even with the layout fixes above, Weighing's 10-column table (`Load`, `I↓/I↑`, `ΔL↓/ΔL↑`, `E↓/E↑`, `Ec↓/Ec↑`, `mpe`) plus the 320px guided panel could still exceed a real laptop's available width (a 1280–1440 CSS-pixel viewport shrinks well below that under 125%+ OS display scaling, a non-maximized window, or dev tools open) — the table clipped against `overflow-x-auto` and had to be scrolled mid-entry, exactly the "doesn't work as a workstation" complaint the previous task was chasing. The fix scales the table down to fit instead of leaving it to clip or requiring the technician to zoom out.
- **Dynamic sizing (real CSS values via a measured scale factor), not `transform: scale()` — a deliberate choice, not the default.** A `transform` was evaluated and rejected: this exact table depends on `position: sticky` for its Load column, AND `GuidedEntryPanel.jsx` targets table `<input>`s directly via DOM refs (`inputRefs`, `.focus()`/`.select()`, browser-native scroll-into-view-on-focus) — precisely the two mechanisms a scaled ancestor is documented to desync (sticky offset math breaks inside a scaled containing block; a transformed element's on-screen hit-box and its DOM geometry/`getBoundingClientRect()` can diverge, and focus-driven auto-scroll math is computed against untransformed layout). Scaling real values sidesteps all of it: every `<input>` keeps its own genuine size, position, and hit-box; only the numbers driving font-size/padding/input-height shrink.
- **Mechanism** (`WeighingFormTable.jsx`): a small `useAutoScale(naturalWidth, floor)` hook attaches a `ResizeObserver` to the table's `overflow-x-auto` wrapper (renamed conceptually to "auto-scale measuring point," though it's the same element) and turns its measured `clientWidth` into `scale = clamp(width / naturalWidth, floor, 1)`. `naturalWidth` is `720` — the table's own previous static `min-w-[720px]`, i.e. "the width this table was designed to look right at." The scale is written to one CSS custom property, `--tscale`, via inline `style` on the `<table>` element, and every size-bearing Tailwind utility inside the table (`text-xs`, the `px-2`/`px-1`/`py-1` cell padding, the input's `h-7`) was replaced with an arbitrary-value class computing off it — e.g. `text-[calc(0.75rem*var(--tscale))]`, `h-[calc(1.75rem*var(--tscale))]` — instead of a second, independent measurement/state path per property. One observed width in, one custom property, every scaled class reads the same value; there is exactly one source of truth for "how scaled are we right now."
- **Scale-down only, with a readability floor, falling back to the pre-existing scroll behavior below it.** `Math.min(1, ...)` in the clamp means the table never scales ABOVE its natural size on a large monitor — no upscaling. The floor is `10/12` (≈0.833): `text-xs` is 12px, and table numerals are never allowed to render under ~10px. Below the floor, the table stops shrinking — its `<table>` keeps an explicit `minWidth: 720 * (10/12) = 600px` (a fixed threshold, independent of the live measurement) so once the wrapper is narrower than that, the table can no longer be squeezed to match it; the wrapper's own `overflow-x-auto` (unchanged, pre-existing) takes over exactly as it did before this task, with text pinned at the 10px floor rather than shrinking further into illegibility.
- **Vertical fit — the table's own scroll region, not the whole page's.** The same wrapper gained `overflow-y-auto` and `max-h-[65vh]` alongside its existing `overflow-x-auto` (`overflow-auto` covers both axes; it is a cap, not a forced height, so a short load sequence shows no scrollbar at all). `<thead>` was made `sticky top-0` (relative to this same scrolling wrapper) so both header rows stay pinned while only the body rows scroll beneath them — on a long load sequence, the technician scrolls the table's rows without losing the column headers, the Passed/Failed line, Remarks, or the guided panel (all of which sit outside this inner scroll region) out of view. This vertical stickiness composes cleanly with the Load column's pre-existing horizontal `sticky left-0` — two independent axes on different elements (the header row-group vs. individual first-column cells), not a conflict; a technician scrolled into the middle of a long table still sees both the column headers AND which load's row they're on. A focused `<input>` still auto-scrolls into view inside this container via the browser's own default focus behavior, so `GuidedEntryPanel.jsx`'s Enter-to-advance needed no changes to keep working with a taller-than-viewport table.
- **Interaction verified, not just assumed** (no visual regression testing tool available in this sandbox; reasoned through against the actual DOM/CSS mechanism): (1) **Click targets** — real inputs, real `<td>` boxes, sized by real (scaled) CSS; the browser's hit-testing and the DOM's own geometry are the same box, so there is no coordinate desync of the kind `transform: scale()` risks. (2) **Focus/typing** — nothing about `<input>` identity, `onChange`, or the ref-callback that populates `inputRefs` changed; only `className`/inherited `font-size` changed. (3) **Sticky Load column** — `position: sticky` was left completely alone (same `left-0`/`z-10`/box), and scaling font/padding via a custom property never touches an element's `position` or removes it from the sticky containing block the way a `transform` on an ancestor would. (4) **Active-cell highlight** — `inputCell`'s `isActiveCell` check and its `bg-amber-200 ring-2 ring-inset ring-amber-500` classes are untouched; they still target the exact same `<td>`. (5) **Guided panel Enter-to-advance / scroll-into-view** — `GuidedEntryPanel.jsx` was not edited at all; its `target?.focus()` calls a real DOM node inside a real (if now internally scrollable) container, and focus-triggered scrolling is native browser behavior that doesn't care whether the container's height is capped by `max-h`.
- **The other six test tables did not need this.** None of them share a column with a fixed-width side panel — Zero-tare/Eccentricity/Sensitivity/Discrimination/Tilting/Repeatability each render their table inside their own centered, capped sheet (`max-w-3xl` to `max-w-5xl`, i.e. 768–1024px) with no competing sibling column, and every one of those tables' own `min-w-[…]` (480–720px) is comfortably smaller than its sheet's content width at any laptop viewport this task targets. They were re-read for this task to confirm the fit and left unmodified — a change here would have been scope creep with no problem to fix.

**Height-constrained layout, no page scroll on a ~720px-tall viewport (`fix/vertical-fit-no-page-scroll`).** Production feedback, on the user's actual (and likely demo) machine: a 1280×720 laptop screen still forced page scrolling to reach the bottom table rows, Passed/Failed, Remarks, and the guided panel's own buttons — the previous task's `max-h-[65vh]` capped the TABLE, but the PAGE itself (chrome above it, plus the page's own natural document flow) still scrolled, because too much fixed vertical space was spent above the table before any of that cap even applied. Two changes, both gated at the SAME `lg` breakpoint (1024px) the two-column table+panel layout already switches on — below `lg`, everything in this section is unchanged from before this task (plain document flow, normal page scroll, the existing stacking fallback):
- **Chrome collapsed, applied to all seven test-entry pages.** `FocusedBackLink` (a full-width bordered pill) followed by a separate `PageHeader` (a 2xl heading with its own `mb-6`) cost ~115px of vertical chrome before any table content, on every one of the seven pages. Replaced by one new component, `FocusedPageHeader` (`src/components/AppShell.jsx`) — back-link pill, a middle dot, the title, all on one ~30px row — used by every `*SessionPage.jsx` in place of that pair. `FocusedBackLink` is deleted (fully absorbed into `FocusedPageHeader`, not left as unused dead code). `FocusedShell`'s own top bar (`py-2` → `py-1.5`) and `<main>`'s vertical padding (`py-4` → `py-3`, `lg:py-2`) were also tightened, and `CollapsibleFormHeader`'s always-visible summary strip (`py-2` → `py-1.5`) — small individually, but every one of these is shared across all seven pages, so each edit is a one-line change with a seven-page payoff. Each `*FormTable.jsx`'s own workstation sheet padding was cut too (Weighing: `p-4 sm:p-6` → `p-2 sm:p-3`; the other six, which previously reused the same `p-6 sm:p-8` for both their collapsed header sheet AND their workstation sheet, had ONLY the workstation one cut, to `p-3 sm:p-4` — the collapsed header sheet's padding is irrelevant to the default vertical budget since it's hidden until expanded), and each form's Passed/Failed and Remarks blocks lost their `mt-5` margins (`mt-3`) with the Remarks `<textarea>` itself shrunk (`min-h-14`/`min-h-16` → `min-h-10`) — still enough to see it's there and start typing, not a fixed 1:1 reproduction of the paper form's blank space.
- **The page container becomes fixed-height and non-scrolling, only at `lg`.** `FocusedShell` (`src/components/AppShell.jsx`) gains `lg:h-dvh lg:overflow-hidden` (the base `min-h-screen` stays for the sub-`lg` case, where the page still scrolls normally). `<main>` becomes `lg:flex lg:min-h-0 lg:flex-col`, so `<Outlet/>`'s root element — each `*SessionPage.jsx`'s own wrapper `div` — receives a REAL, definite height to size against (`lg:flex-1 lg:min-h-0` on that wrapper), not just `auto`. Every `*SessionPage.jsx` hands that height straight through to its form: the form is wrapped in a `lg:min-h-0 lg:flex-1` div (Weighing: `lg:overflow-hidden`, since its table has its own internal scroll region below; the other six: `lg:overflow-y-auto`, since their forms have no internal scroll mechanism of their own, so the WHOLE form sheet scrolls together as the safety net if it doesn't fit — simpler than building six more sticky-thead table-scroll regions for content that's short enough this rarely engages). Nothing in this chain uses a grid track for the height-passing itself — a CSS Grid track stays content-sized even inside an `h-full` grid container (a well-known gotcha), so every height-passing container in this chain is `flex`, not `grid`, specifically so `flex-1`/`h-full` percentages resolve the way they look like they should.
- **Weighing gets the full treatment: table body is the one thing that scrolls.** `WeighingFormTable.jsx`'s outer two-column container switches from `grid-cols-[minmax(0,1fr)_320px]` to `lg:flex lg:h-full lg:min-h-0` (column widths now come from the columns' own `lg:flex-1` / `lg:w-[320px]`, not `grid-cols`) — a flex row's `align-items: stretch` default makes both columns genuinely fill the real height, sidestepping the grid-track gotcha above. The left column becomes `lg:flex lg:h-full lg:min-h-0 lg:flex-col`: the collapsed header strip is `lg:shrink-0` (never compressed under space pressure — the table sheet below, with `lg:flex-1`, is the one element actually designed to grow/shrink), the table sheet itself is `lg:flex lg:min-h-0 lg:flex-1 lg:flex-col`, and INSIDE it, the table-scroll wrapper's fixed `max-h-[65vh]` (the previous task's guess, kept unchanged as the sub-`lg` behavior) is replaced at `lg`+ by `lg:max-h-none lg:min-h-0 lg:flex-1` — the table's real remaining height (whatever Passed/Failed and Remarks, both `shrink-0` below it, didn't spend), not a guessed viewport fraction. `<thead sticky top-0>` (previous task) is unchanged and still does its job inside this now-precisely-sized scroll region. The right column (guided panel) drops `lg:sticky lg:top-4` — the page no longer scrolls at `lg`+, so sticky positioning has nothing to stick against — for `lg:h-full lg:w-[320px] lg:shrink-0 lg:overflow-y-auto`: it fills the same height the left column fills (flex stretch) and scrolls internally ONLY if its own content doesn't fit. No reordering of the panel's own JSX was needed for requirement "keep input + adjust buttons + Next always visible, even if something must scroll": the panel's DOM order already puts title → applied-load box → input → adjust buttons → Previous/Next BEFORE "Last recorded" and the footer instructions text, so a plain top-anchored `overflow-y-auto` already reveals the primary controls first and only asks for a scroll to reach the lower-priority trailing content.
- **Height budget at 1280×720 (reasoned through, not measured in a real browser — no visual tooling in this sandbox):** top bar ~33px + `<main>` padding ~16px + `FocusedPageHeader` row ~28px + gaps ~16px + collapsed header strip ~30px + table sheet border/padding ~28px + `<thead>` (2 rows) ~52px + Passed/Failed ~58px (incl. its own margin) + Remarks ~78px (incl. its own margin, shrunk textarea) + footnote ~24px ≈ **363px of fixed chrome**, leaving **~357px** for the table's own scrollable row region out of 720px total — comfortably more than the ~100–150px this task targeted reclaiming (chrome dropped from the ~305px the user measured to well under half that once cut). At ~26px/row (unscaled `text-xs` + padding), 357px shows roughly 13 rows before the table's own internal scroll engages — most Weighing load sequences never need to scroll at all. The guided panel gets the same ~635px (720 − topbar − main padding − page-header row − gap) the left column gets, against its own natural content height of roughly ~500px — also no scroll needed in the typical case, with the internal `overflow-y-auto` there purely as the "content taller than expected" safety net requirement 3 asked for.
- **Larger and narrower screens.** Above 1280×720, the same fixed-chrome total leaves MORE room for table rows (more of the load sequence visible before the internal scroll engages) — nothing about the mechanism assumes exactly 720px, it just divides whatever height `<main>` actually has. Below `lg` (1024px), none of this section's classes apply — the existing sub-`lg` behavior (plain document flow, page-level scroll, the panel stacked above the table via `order-1`/`order-2`, the table's own `max-h-[65vh]` cap) is completely unchanged, exactly matching the "existing stacking/scroll fallback" this task was told not to break.

## PDF & audit

**Certificate PDF generation** (`POST /api/sessions/{id}/report`, `app/routers/sessions.py`) — approver/admin OR the session's own creator (this action isn't separation-of-duties-sensitive: generating a copy of your own already-issued certificate needs no such gate), only when the session's status is `issued` (409 otherwise, via the same `ensure_status`/`InvalidTransition` machinery the lifecycle transitions use). Reproduces, for report fidelity only (never a copy of the copyrighted OIML document): the instrument's page-6 identity/registration fields, verification type, certificate number, issue date, the Weighing test's full load/`I`/`ΔL`/`E`/`Ec`/mpe/pass-fail table (the OIML clause 8.3.3 checklist's priority item, per this task's own scoping), and a one-line PASS/FAIL/Incomplete/Not-performed summary for each other test actually performed — Zero/tare device accuracy, Repeatability, Eccentricity, Discrimination, Tilting, Sensitivity. Built with `reportlab` (added to `backend/requirements.txt`), entirely in memory (`io.BytesIO` — CLAUDE.md: never local disk); the QR code uses reportlab's own built-in `graphics.barcode.qr.QrCodeWidget`, not a second `qrcode` dependency.
- **Data assembly is split from rendering, for testability.** `app/services/certificate.py` (pure — no DB, no reportlab) takes already-fetched rows/service outputs and shapes a `CertificateData`; `app/pdf/certificate.py` (reportlab only, no DB) renders that into bytes. Each test's aggregate is computed the RIGHT way, not by one naive rule everywhere: Weighing/zero-tare/eccentricity/discrimination/sensitivity have no whole-set pass criterion, so "every reading's own stored `passed`" is a complete, correct verdict; Repeatability's real verdict needs BOTH the per-reading mpe check AND the spread check, so it's recomputed via `app.services.repeatability.compute_series` (same function its own GET route calls) rather than read naively off `test_results.passed`; Tilting's per-reading `passed` is always `None` by design (its criteria are whole-dataset properties), so its real verdict comes from `app.services.tilting.compute_state` (again, the same function its own GET route calls) — see `app/services/certificate.py`'s own docstring for the full reasoning.
- **The QR code encodes the FULL public verify URL**, not just the certificate number — `https://<domain>/verify/{certificate_number}`, built from the incoming request's own `request.base_url` (correct automatically on production, any Vercel preview deploy, and local dev, since frontend and backend share one origin) with an optional `PUBLIC_APP_BASE_URL` env-var override if that assumption is ever wrong behind some other proxy layer.
- **Storage, never local disk** (CLAUDE.md) — `app/repositories/storage.py`'s `upload_report_pdf` writes to the `reports` bucket (`SUPABASE_STORAGE_BUCKET` env var, default `"reports"`) at a deterministic `certificates/{certificate_number}.pdf` key, with `upsert` so regenerating a report for the same session is idempotent rather than erroring on "already exists." Uses the CALLER's own per-request user-scoped client, same as every other write in this app — never service-role — so an upload's success depends on the `reports` bucket's own Storage-level policies permitting an authenticated user to write there; this is a genuinely unverified assumption until the next real deploy (same honesty this project already applies to ADR-0006's build-time `engine/` copy), flagged here rather than silently reached for the service-role key.
- **Recording `report_storage_path` needed its own function (ADR-0009), not a plain `.update()`.** Once a session is `issued` it matches NO UPDATE policy on `test_sessions` at all (Session lifecycle, above) — by design, so an issued certificate's content can never be altered. `public.set_report_storage_path(p_session_id, p_path)` is a narrow, `SECURITY DEFINER` exception scoped to exactly that one column, re-checking the same creator-or-approver/admin authorization the API layer already enforces before ever calling it. Called via `sessions_repo.set_report_storage_path`, and deliberately **non-fatal** if it fails (logged, not raised) — unlike the return-reason audit write, `report_storage_path` is fully deterministic from `certificate_number` alone, so nothing is actually lost if this one bookkeeping write fails; the already-generated, already-uploaded PDF is still returned to the caller.
- **The PDF bytes are returned directly** in the HTTP response (`Content-Disposition: attachment`), not a signed URL — simpler, and avoids needing the generated URL's own access policy to independently match the authorization this endpoint already enforces.

**Public verification** (`GET /api/verify/{certificate_number}`, `POST /api/verify/{certificate_number}/report-discrepancy`, `app/routers/verify.py`) — the ONE part of this API with no `Depends(get_auth_context)` at all, by design: a citizen or field inspector scanning a certificate's QR code has no ScaleCert account. See **ADR-0009** for the full reasoning; summarized:
- **`get_public_certificate_info(p_certificate_number)`** (`db/schema.sql`) is a `SECURITY DEFINER` Postgres function — the ONE deliberate anonymous-read exception in this entire schema (no RLS policy anywhere else permits an anonymous SELECT, correctly). It returns exactly `certificate_number`, `status`, `instrument_model`, `instrument_manufacturer`, `instrument_type_designation`, `accuracy_class`, `verification_type`, `issued_at` — its own `WHERE status = 'issued'` clause means a certificate number that doesn't exist, or belongs to a `draft`/`submitted`/`approved`/`returned`/`superseded` session, comes back as zero rows, indistinguishably: the API can never leak whether a non-issued session with that number exists. Never returns technician/approver identity, raw readings, internal ids, or remarks. `app.contracts.verify.PublicCertificateOut` mirrors this exact field list (`extra="forbid"`) — a future accidental addition to the function's `SELECT` would need a matching, equally deliberate model change, never silently pass through.
- **Called via `app.supabase_client.anon_client()`** (pre-existing, unused before this task) — the one place in the whole backend that doesn't build a per-request user-scoped client, since there is no user to scope to. Safety here comes from WHAT the function exposes, not from WHO is asking: the anon key alone grants no ability to query any table directly.
- **`GET /verify/{certificate_number}`** returns the safe fields on a hit, or a plain 404 (`{"detail": "certificate not found"}`) — the SAME 404, byte-for-byte, whether the number never existed or belongs to a non-issued session.
- **`POST /verify/{certificate_number}/report-discrepancy`** (`DiscrepancyReportIn`: `description` required 1-4000 chars, `contact` optional) inserts into `discrepancy_reports` via a single-purpose RLS policy (`discrepancy_insert_anon ... with check (true)`) rather than a function — simpler for a plain, unconditional insert; there is no matching anonymous SELECT policy, so a report can never be read back except by `admin`. **Deliberately does not validate that `certificate_number` corresponds to a real or issued certificate** — checking would itself create a side-channel leaking exactly the distinction the GET route above is careful never to leak. No rate-limiting: a correct one needs durable, cross-invocation state (a Postgres-backed counter, or edge middleware), which an in-process limiter cannot provide on Vercel's stateless/ephemeral functions — noted as a follow-up, not built here.
